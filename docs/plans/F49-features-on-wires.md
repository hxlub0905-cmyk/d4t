# F49 — 特徵也走線：判定與 Output 進 DAG（範圍評估）

**狀態：只是範圍評估，一行程式都還沒動。** 使用者 2026-08-28：
「我是真的想要讓判定跟 output 變成 DAG 節點」。

---

## 0. 先更正題目：Output 卡**已經是**節點了

`output_report` / `output_klarf` / `output_char` 都在 `recipe.nodes` 裡、都畫在
畫布上、都排在 `execution_order` 裡。它們缺的**不是節點身分，是埠** ——
它們吃特徵的那 5 個參數（`rank_by`、`plot_features`、`size_feature`、
`columns`）用的是**名字**，畫布上因此沒有任何一條線指向它們。

判定缺的比較多（連節點都不是），但**缺的那一半是同一件事**。

> 所以這一輪真正的題目是：**讓「特徵」跟影像流、具名區域一樣走線。**
> 判定與 Output 是它的兩個受益者，不是兩個獨立的工程。

## 1. 好消息：F42 剛做過同一個形狀

[`F42-region-edges-plan-b.md`](F42-region-edges-plan-b.md)（2026-08-27）把
**具名區域**從「參數裡的一個名字」搬成「`recipe.edges` 裡的一條線」，
五個階段、逐段驗黃金值、證明是純重構。那份文件就是這一輪的樣板：

| F42 | 做了什麼 | F49 對應 |
|---|---|---|
| **B0** | 撞名 → error（**前置條件**）| ⚠ 這一格在特徵上難很多，見 §2 |
| **B1** | 引擎認得新的一種線（`is_region_edge`）| `is_feature_edge`，同一支判準函式的形狀 |
| **B2** | UI 拉線走真的 `add_edge`，參數從線水合 | Output 卡照抄；判定不行，見 §3 |
| **B3** | 遷移（判準是 `version < RECIPE_VERSION`）| 同 —— `RECIPE_VERSION` 2 → 3 |
| **B4** | 拆舊路、文件改成現在式 | 同 |

F42 選 B（存進 edges）而不是推導，理由記在它的 §2：
**「對齊比較安全 —— 兩套機制本身是每次改動都要多想一次的稅。」**

## 2. 壞消息：B0 那一格在特徵上完全不一樣

F42 的 B0 買到的東西寫得很清楚：

> 線指著**一個特定的節點**，而引擎那一頭沒有節點的概念（`ctx.set_roi` 是
> 同名覆寫）。名字唯一的時候這兩件事是同一件事：**線指的那張卡 ＝ 引擎真的
> 給的那個框**。撞名的時候不是。

**特徵的處境一模一樣，但不能用同一招解決** —— 因為特徵撞名是**正常的**：

* `ctx.features` 是一個平的 dict，後寫的贏；
* `clip_frac` 每一張 Enhance 卡都產出、`glv_pixels` 每一張 GLV 都產出 ——
  **每一份健康的 recipe 都在撞名**（`_feature_collisions` 對「兩邊都是診斷」
  刻意不報，理由是「每一份 recipe 都出現的警告會被學會忽略」）；
* 而且引擎**有救援機制**：被蓋掉那一份改叫 `<節點 id>_<特徵名>`。

所以 F42 那句「直接禁止撞名」在這裡是**不能做的**（會把每一份正常 recipe 判成
錯的）。可走的兩條：

| | 做法 | 代價 |
|---|---|---|
| **B0-a** | 線的 `src_out` 存**救援後的唯一名字**（也就是 `ctx.features` 真正的鍵），不是使用者看到的裸名 | 線與畫面上的名字不一致，要一層對照；改上游會讓鍵改名（F37 那條「多接一條區域線會改掉每一個名字」的坑放大） |
| **B0-b** | 特徵改成**每個節點自己的命名空間**（`node.feature`），平的 dict 只留相容視圖 | 改的是引擎的身分模型 —— F42 的 P1-b **明確拒絕**做這件事；分數表達式、判定樹、CSV 欄名全部受影響 |

**這一格是整個 F49 的真正風險，不是判定或 Output。**

## 3. 判定跟 Output 難度差很大 —— 不要綁在一起做

| | Output 三張卡 | 判定 |
|---|---|---|
| 依賴住在哪 | **參數**（`feature_key` / `feature_keys`，共 5 個）| **自由文字的算式**（樹的 `when`、`let.expr`、`score`）|
| F42 樣板適用嗎 | ✅ 幾乎逐字適用 —— 區域也是參數 | ❌ 算式不是參數，沒有一格可以當埠 |
| 要動什麼 | 型別表多一組 `FEATURE_TYPES`、`is_feature_edge`、水合、埠的畫法 | 以上全部 ＋ `decide` 從頂層鍵搬進 `nodes` ＋ `type="tree"` 參數 ＋ 70 處引用 |
| 節點身分 | 已經有 | 要新建 |

而判定還有一個 F42 沒遇過的**方向問題**：

* 區域：**線是真相**，參數是從線水合出來的唯讀顯示；
* 判定：**算式是真相**（使用者打 `glv_median > 12` 就該成立），線只能是它的
  投影 —— 否則使用者每打一個變數名就要去拉一條線。

也就是說判定的線是**推導出來的**，而 F42 B4 才剛把一條推導出來的線
（`region_lines()`）刪掉，理由是「兩份相加、每條線被畫兩次」。
要做就要明講：**判定的線是算式的投影，只有一個真相（算式），所以不會有兩份。**
那跟 F42 刪掉的那一份不是同一回事，但這句話要寫在程式碼上，不然下一個人會
照 F42 的結論把它清掉。

## 3.5 使用者的授權依據（2026-08-28）

> 「如果不一致，會有兩套準則，真正的使用者反而不知道怎麼用。」
> 「使用者是不會寫 code 的人，但只要他看得懂每張 card 的意義、知道每張 card
> 在幹嘛，那他就能用拉線去達到他想要的事。」

**這句話跟 F42 §2 選 B 的理由是同一句**（「兩套機制本身是每次改動都要多想
一次的稅」），只是從使用者那一面講。所以「統一」在這一輪**不是軟價值，是主要
需求** —— 評估的時候不可以再把它當成「順便的好處」折價。

由此推出一條驗收條件，寫在這裡免得做到一半漂掉：

> **一個手勢。** 使用者要把任何東西從一張卡送到另一張卡，動作永遠是「從這裡
> 拉一條線到那裡」—— 不管那個東西是影像、區域，還是一個數字。

## 4. 要改的東西（清單）

量出來的規模：

| 面 | 數字 |
|---|---|
| 產出特徵的卡 | **13 張** |
| 吃特徵的參數 | **5 個 / 3 張卡** |
| `recipe.decide` 引用 | **70 處 / 11 支模組** |
| 碰到 `edges` / `add_edge` 的程式碼 | **79 處** |
| 碰到 edge/port 的測試檔 | **50 支** |
| 畫布 | `ui/canvas.py` **2,083 行** |

逐項：

**core**
- `step.py`：`FEATURE_TYPES`（`feature_key` / `feature_keys`，表要有唯一的家，
  同 `IMAGE_TYPES` / `REGION_TYPES`）
- `recipe.py`：`is_feature_edge`、`execution_order` 認它、`validate` 的
  `unknown-feature*` 三條改成問線、`RECIPE_VERSION` → 3 ＋ 一道遷移
- `engine.py`：`_eval_decision` 從「跑在 DAG 之後」變成「一個節點的 run」
- `batch.py`：`redecide` / `apply_lot_scaling` 的呼叫點跟著搬
- **快取簽章**：特徵線影響結果 → 鐵則 9，必須進簽章

**ui**
- `canvas.py`：第三種埠與線（影像＝實線圓埠、區域＝虛線菱形埠、特徵＝?）
- `viewmodel.py`：水合、undo/redo、刪卡時的連動（F42 B2 的「一支水合五個入口」）
- `tree_panel.py` / `tree_scene.py`：判定變節點之後的歸屬
- `studio.py`：接線（`_node_problems` 的 `node_id=None` 問題順便消失）

**驗收**
- 黃金值三份**逐階段**驗（F42 的做法：B0→B4 每一段都跑 `--check`）
- `to_json_dict → from_json_dict` 是 identity（鐵則 9）
- 出貨的兩份 recipe 重存成 v3，證明每一張卡、每一條線、每一條 route 逐項相同

## 4.5 埠會爆炸 —— 而畫布已經解過這題

實測出貨的兩份 recipe：

| | `patch-dsnr-by-class` | `ebi-to-api-characterization` |
|---|---|---|
| 節點 | 7 | 4 |
| 現有的線 | 6 | 2 |
| **特徵輸出埠（如果一個特徵一個埠）** | **45**（`glv_stats` 一張就 **29** 個）| **15** |
| **判定真正要拉的線** | **3** | **3** |

一張 29 個埠的卡：`_PORT_PITCH = 13`，節點高度會變成 `13×29+10 = 387 px`。
**不可用。**

好消息是這題**畫布已經答過**：`canvas._MAX_PORTS = 4` ——
「一個節點最多畫幾個影像輸出埠（**再多就擠不下，退回單一埠**）」。

所以特徵的埠設計照抄那個結論，而且更徹底：

* 產出特徵的卡上是**一個**「數字」輸出埠（第三種形狀）；
* 從它拉出來的時候跳一張清單問「哪一個數字」——
  卡片自己答得出來（`resolve_feature_specs`，PR-3 已經有結構化身分了）；
* 那條線把選到的名字存在 **`src_out`** 裡 —— 跟影像線把流名存在 `src_out`
  裡**一模一樣**，不是新機制。

**埠 45 個 vs 線 3 條**這個落差正是它可行的原因：使用者只為他真的要用的那
幾個數字拉線，其他 42 個從來不畫。

## 5. 建議的切法

**不要一次做。** 三段，每一段自己就有價值、自己就能停：

| 階段 | 內容 | 風險 | 停在這裡也成立嗎 |
|---|---|---|---|
| **F49-1** | 特徵撞名的身分問題（§2 選 a 或 b）＋ `is_feature_edge` ＋ 引擎認線 | 高（真正的難點）| ✅ 引擎更嚴謹，畫面不變 |
| **F49-2** | **Output 三張卡的埠**（F42 樣板逐字適用）| 中 | ✅ 已經買到「Output 不再是孤島」 |
| **F49-3** | 判定變節點（`type="tree"`、70 處、算式投影成線）| 高 | — |

⚠ **F49-1 要先做，而且它是唯一一段沒有畫面產出的。** 跳過它直接做 F49-2 的
話，線指的那張卡跟引擎真的給的那個值可以不是同一個 —— 那正是這個 repo 已經
踩過**七次**的形狀，而 F42 §3 整段就是在講為什麼那一格不能跳。

## 5.5 ⚠ 會遇到的問題（完整清單）

按「會不會讓事情安靜地錯」排，不是按工作量排。

### P1 · 撞名與救援 —— 線指的卡 ≠ 引擎給的值（§2）
最嚴重，因為它正是這個 repo 踩過七次的形狀。**F42 的解法（直接禁止）在這裡
不能用**：`clip_frac` / `glv_pixels` 這類診斷數字每一張同類卡都產出，撞名是
每一份健康 recipe 的常態，而引擎有救援機制（`<節點 id>_<特徵名>`）。
→ 兩條路寫在 §2，**必須先決定**。

### P2 · 上游改一個設定，下游的線全斷
量測卡的前綴是**條件式**的：在既有的卡上多接一條區域線，它寫的每一個名字都
會改（`glv_median` → `epi_glv_median` ＋ `mg_glv_median`，F18/F37）。
今天的下場是一條 `stale-feature-ref` warning；**改成線之後那是一批斷掉的線**。

> 這其實是**變好**（斷掉看得見，勝過安靜退化），但要有人接住：
> 改名的時候要跟著改寫 `edges` 的 `src_out`。對照表已經在
> `Step.legacy_feature_renames`（F18 建的），但它現在只服務**檔案遷移**，
> 不服務**畫面上的即時編輯**。這一段是新的。

### P3 · 判定的依賴在算式裡，方向跟區域相反（§3）
區域是「線是真相、參數是投影」；判定只能是「算式是真相、線是投影」——
否則使用者每打一個變數名就要去拉一條線，而那違反 §3.5 那句「他看得懂卡就能用」。
→ 要明講這個例外，不然下一個人會照 F42 B4 的結論把推導出來的線清掉。

### P4 · 「跟整批比」要來回，而 DAG 不會來回
`Let.scale` 是兩趟的（逐顆 → 整批算 z → **回頭重判**，`apply_lot_scaling`
→ `redecide`）。判定一旦是 DAG 上的節點，那個「回頭」就要有地方站。
引擎現在是三個寫死的階段，不是一張會交錯尺度的圖。
→ `Step.scale`（`SCALE_DEFECT` / `SCALE_LOT`）這個概念已經在了，缺的是
`execution_order` 會按尺度分段。**F49-3 躲不掉這一格。**

### P5 · 有線 ≠ 這一顆有值
F19 定的規矩是「**算不出來的那一格不寫**」。所以一條接好的特徵線，在某一顆
defect 上可能什麼都沒帶。畫面不可以讓「線接好了」讀起來像「一定有值」——
今天的 `decide_unanswered` 就是在講這件事，它要留著。

### P6 · 線會變多，而那正好打到你要的東西
判定 3 條、Output 卡最多 5 條 —— 以出貨的 recipe 看是 **+3 到 +8 條**，
不算爆炸。但那是**現在**的 recipe；使用者真的開始用「拉線挑數字」之後會拉
多少沒有人知道。
→ 驗收要拿一份**故意接很多**的 recipe 看畫布還讀不讀得動，不要只用現有的兩份。

### P7 · 快取簽章（鐵則 9）
特徵線會影響結果 → **必須進簽章**。漏掉的症狀是「改了接線、分數沒變」，
而那在這個 repo 有前科。

### P8 · 50 支測試碰到 edge/port
不是風險，是工作量：既有的測試多半假設「edges 裡只有影像線與區域線」。
`is_feature_edge` 加進去之後要逐支確認它們問的還是原本那件事。

## 6. 還沒問使用者的兩件事

1. **§2 的 B0-a 還是 B0-b**（線存救援名 vs 特徵改成每節點命名空間）。
   b 比較乾淨，但 F42 的 P1-b 明確拒絕過動引擎的身分模型 —— 那個拒絕的理由
   在這裡還成不成立要重新問一次。
2. **判定的線是推導出來的**（§3），這跟 F42 剛拆掉的那條路長得像但不是同一件
   事。要不要接受這個例外。
