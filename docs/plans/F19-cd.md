# F19 — CD 整張重做（Measure 段第二張卡）

**狀態：引擎與 UI ✅ 收斂 2026-08-21。** 第二批（無方向那一支）見 §9。

---

## 1. 為什麼重做

`cd_measure` 量的是「接進來那個區域的 bounding box 寬高」，`area_px = 寬 × 高`。
檔頭自己註明「這張卡之後會重做（F16）⋯⋯這一輪只把名字與訊息修對，演算法一行
都沒動」。使用者原話（`F18-glv.md` §9.1）：**「基本上要全部砍掉」**。

三個實質問題：

1. **bbox 的變異數不隨樣本數下降。** 它是極值統計量 —— 邊界上任何一顆離群
   像素 100% 傳進答案，圖再大、雜訊平均得再好都不會改善。對一個要拿去跟門檻
   比大小、逐顆比較的量測，那是結構性的，不是「精度差一點」。
2. **它在既有 fixture 上是一個常數。** 兩份 fixture recipe 的 cd 卡都沒接
   區域 → 三份黃金值裡每一顆都是 `128 / 128 / 16384`（整張 patch），而 score
   表達式一個 `cd_*` 都沒用到。也就是它對那批資料的鑑別力是零，而 CSV 上看
   不出來。
3. **`refine="subpixel"` 只精修 Y、只取 bbox 中心那一欄**，`cd_x_px` 永遠是
   整數，而參數名沒有透露這件事。

### 這一輪的範圍（使用者 2026-08-21 定調）

| 決定 | 內容 |
|---|---|
| 範圍 | **只做「有方向」那一支**（線寬／溝寬：掃描線 ＋ LWR/LER）|
| 相容性 | **舊特徵完全刪掉，以新的為主**（原話：「就得完全刪掉 以新的為主」）。不做遷移、不留相容層 |
| 面積的界線 | 門檻切割**可以**做，但**只在區域內、且不產生具名區域** —— 它不去找有哪些缺陷，只量使用者已經指給它的那一塊。留給第二批 |

## 2. 核心：原子單位是「一條量測線」

```
   ✗ 以區域為單位（重做前）            ✓ 以量測線為單位

   ┌─────────────┐                    ┌─────────────┐
   │   ░░███░░   │  bbox 寬 = 5       │ ──░░███░░── │ ← 4.83
   │   ░░███░░   │                    │ ──░░███░░── │ ← 4.91
   │   ░░████░   │ ← 一顆雜訊像素      │ ──░░████░── │ ← 5.07 ← 只污染這一條
   │   ░░███░░   │    決定整個答案     │ ──░░███░░── │ ← 4.88
   └─────────────┘                    └─────────────┘
     一個數字、沒有誤差棒                平均是 CD、**σ 就是 LWR**、
                                        min 是頸縮、max 是橋接
```

粗糙度不是另外加的功能，是本來就在算的那組距離的標準差。一件事做對了順便長出
第二件事 —— 那通常代表抽象切在對的地方。

**兩條邊各自的 σ 是 LER**，而它跟 LWR 不是同一件事：兩條邊一起晃（LER 有、
LWR 沒有）是載台或對位在漂，各自晃才是結構本身粗糙。兩個不同的製程故障，
而 bbox 那條路連問都問不出來。

## 3. 四個彼此正交的問題

沿用 F18 拆 Gray level 的辦法：

| | 問題 | 參數 |
|---|---|---|
| ① | **在哪量** | `source`（流）× `roi`（區域）—— 畫布上的線 |
| ② | **沿哪個方向** | `axis` = auto/x/y；`target` = auto/bright/dark |
| ③ | **邊界怎麼定義** | `criterion` ＋ `threshold_pct` ＋ `window` |
| ④ | **一串距離怎麼收** | `report` 膠囊 ＋ `target_cd` |

**刻意不採用「四個 method（profile / contour / edge_pair / bbox）」那種分法**
（使用者指定）：那四個選項每一個都同時綁死②③④，使用者改一件事實際上動了三件，
而畫面上只有一個下拉在動。判準只有一句話：

> **這個參數問的是使用者的樣品，還是問軟體？**
> 「這條線是亮的還是暗的」問樣品；「用 profile 還是 contour」問軟體。
> 後者不該出現在卡片上。

## 4. 判準：一個被實測推翻的預設 ★

計畫寫的是「預設用 `fit`（整段爬升線性化擬合 erf），因為穿越法只吃跨過門檻的
**兩顆**像素（誤差 ≈ σ/斜率），擬合吃整段爬升（≈ σ/斜率/√N）」，並要求第 1 步
產出實測表當證據。

**表出來了，而它推翻了那個推論。**
（真值 12.00 px、blur 1.5、200 次；`tests/test_algo_edge.py::test_criterion_noise_table`）

```
  雜訊     threshold                gradient                 fit
  2.0    bias +0.051 σ 0.055      bias +0.001 σ 0.085      bias +0.065 σ 0.056
  5.0    bias +0.064 σ 0.133      bias -0.001 σ 0.223      bias +0.089 σ 0.139
  10.0   bias +0.060 σ 0.395      bias -0.032 σ 0.551      bias +0.133 σ 0.426
```

兩個原因，都是量了才知道的：

1. **預設的 1 px 平滑已經替穿越法做完了雜訊平均。** 擬合想賺的那個 √N，平滑器
   先賺走了 —— 關掉平滑（`smooth=0`）兩者的 σ 一起變差，擬合也沒有變好。
2. **單邊 erf 模型在有限寬度的線上會被隔壁那條邊污染。** 爬升段的內側樣本裡摻
   了另一條邊的尾巴，擬合看到的曲線因此提早飽和，位置被往外拉 —— 那就是 `fit`
   那一欄偏差恆為正的來源。50% 穿越點落在爬升的正中間，污染最小。

**所以預設是 `threshold`（σ 最小）。** `gradient` 留著的理由是它的**偏差**最小：
對稱的平滑不會移動反曲點，所以它是唯一在 `smooth` 開大時仍然不偏的判準
（實測 `smooth=2.0`：threshold +0.295、fit +0.355、gradient −0.001）——
要跨批次比絕對 CD 的時候選它。

`fit` 沒有刪，因為「不確定的時候先收起來、確定了再刪」是使用者的判斷不是我的
（`CLAUDE.md` §5）。它現在排在三個選項的最後。

> **兩份說法都留在 `algo/edge` 的檔頭**：當初為什麼那樣推、後來量到什麼。
> 下一個人很可能會再推論一次同樣的 √N，然後再改一次預設。

## 5. 演算法（`d4t/core/algo/edge.py`，純 NumPy、零 Qt）

| 函式 | 做什麼 |
|---|---|
| `find_edges` | 一條剖面上的所有邊（候選 → 局部平台 → 三選一的判準）|
| `pair_across` | 把錨點所在的那個結構包起來的兩條邊 |
| `scan` | 在一塊裁好的影像上鋪量測線，每條量一個寬度 |
| `choose_axis` | `axis="auto"` 選哪一軸 |
| `threshold_level` | 門檻的高度（**整個 repo 只有這一份**）|

四個踩過的坑，每一個都有一支測試釘住：

1. **平台不能跨過隔壁那條邊。** 一條 6 px 寬的線在預設視窗 9 之下，左邊那條邊
   的「右側平台」取到的是線**外面**的背景 → 對比被低估 → 門檻高度錯 →
   6.0 量成 7.9。修法是 `_neighbour_halves`：兩條邊之間的樣本一人一半。
2. **門檻的高度要從暗算到亮。** 寫成「從左邊那個平台算起」的話，亮線的上升邊
   量在 25%、下降邊量在 75%，兩條邊同向移動 —— `threshold_pct` 從 25 拉到 75
   量出來是 `12.2348106481077` 對 `12.234810648107693`。**一個看起來有在動、
   實際上沒有作用的旋鈕。**
3. **雜訊估計不能用平台的 MAD。** 一條 10 px 的線，內側「平台」還在爬升，
   MAD 量到的是訊號不是雜訊 —— 完全乾淨的合成影像也只拿到 0.88 的品質分。
   改用整條剖面的**一階差分**（差分把平滑的成分消掉）。
4. **邊的門檻要相對於雜訊，不能只用絕對 GLV。** 見 §6。

## 6. 「量到的是雜訊」——收斂前最後一個坑 ★

拿合成 lot 的 `diff`（一顆小 blob ＋ 雜訊）餵進去：**128 條掃描線 128 條成功**，
真缺陷與假點都吐出 8–10 px 的寬度。跑得完、有數字、每一顆都有、而且量的是雜訊。

根因：候選邊的門檻是「這條線上**最陡的地方**的 35%」，而在一條沒有結構、只有
雜訊的線上，最陡的地方就是最大的那顆雜訊。原本的地板只有絕對值 1 GLV。

修法：`min_quality`（卡片上叫 **Ignore edges weaker than**，預設 0.5 ＝
對比至少是雜訊的四倍）。

> 一般化的一句話：**凡是「找極值再判斷」的演算法都要先問「沒有訊號的時候，
> 極值是誰」。**

## 7. 輸出

**一律吐的五個**（不在膠囊裡）：

| 名字 | 意義 |
|---|---|
| `cd_n` / `cd_lines` | 幾條線量到了／總共放了幾條（比值就是成功率）|
| `cd_axis_deg` | 自動選了哪個方向（0 / 90）|
| `cd_bright` | 量到的是亮的（1）還是暗的（0）那一條 |
| `cd_edge_score` | 邊緣品質 0..1（`對比/(對比+4×雜訊)`，三個判準共用一份定義）|

`cd_bright` 是**實跑合成 lot 才發現要有的**：`target="auto"` 在同一批裡逐顆挑了
不同的極性（patch 的晶格相位逐顆不同），於是 `cd_median` 那一欄同時裝著
「線寬 6.5」與「溝寬 9.4」兩群 —— 每一顆都吐得出正常數字，而 CSV 上沒有任何
東西透露它們量的不是同一種東西。規矩因此寫成一句話：

> **卡片自動做的每一個決定，都要變成一個使用者畫得出分布的數字。**

**膠囊選的**（`report`，重用 F18 的 `MetricChips`，分三群）：

| 群 | id |
|---|---|
| Width | `cd_median`（預設）`cd_mean` `cd_min` `cd_max` `cd_range` |
| Roughness | `cd_std`（預設）`ler_a_std` `ler_b_std` |
| Vs target | `cd_dev` `cd_dev_frac`（要填 `target_cd` 才宣告）|

**一律報 σ，不報 3σ。** LWR 的業界慣例是 3σ，但同一個名字在不同地方算出不同的
東西是這個 repo 最怕的錯 —— 所以名字說 σ，「LWR = 3 × 它」寫在 help 裡。

`target_cd`（使用者從製程規格抄過來）→ `cd_dev` / `cd_dev_frac`。理由：這個工具
沒有校正，「這條線是 43.2 px」對使用者幾乎沒有意義，能拿去分 bin 的是
「**比規格窄了 12%**」—— 而它不需要 two-pass、不需要 lot baseline。

### 失敗政策

| 情況 | 行為 |
|---|---|
| 一條線配不出邊 | 那條不計入，原因累計進 meta |
| **邊落在框或畫面邊界上** | `open_edge`、不計入。**絕不把邊界當成一條邊** |
| `open_edge` 超過一半 | `ctx.warn`，而且講得出下一步 |
| `cd_n < min_lines`（預設 3）| 整組長度特徵**都不寫**（不是 0、不是 NaN），只留計數 ＋ 一句 warn |

## 8. UI

### 8.1 影像上的量測標記（Measure 段共用）

`ImageView` 原本只吃**矩形**。新增 `set_marks(lines, points, focus)` ——
線段 ＋ 每條線上的點，正規化座標。

**資料由卡片自己交出來**（`Step.overlay_marks`，預設什麼都不畫）：meta 的形狀
是那張卡的事，UI 只負責畫。F18 §9.0 把這件事列為整個 Measure 段共用、指名跟
CD 一起做 —— 只給一張卡做一份的話，下一張量測卡進來會有第二份長得不一樣的。

**跟區域框不同來源，不要混**：框從 model 推導（recipe 說要看哪裡），標記來自
跑完的 context（這一顆真的量到了什麼）。混在一起的話，「框還在但標記沒了」
這個最有用的狀態（這一顆量不出來）就講不出來。

線最多畫 24 條（等距抽樣），但**代表那一條一定在裡面** —— 面板上那張剖面圖畫
的就是它，兩邊對不起來使用者就找不到。

### 8.2 面板 `CdInspector`

```
 ┌ Profile of one line ───┐ ┌ Each line ────┐ ┌ Across the batch ┐
 │        ┌────────┐      │ │  │▌            │ │   ▁▂▅▇▅▂▁        │
 │       ╱          ╲     │ │  │▌▌           │ │        ▲ 這一顆   │
 │ ─────╳────────────╳─── │ │  │▌ ← 頸縮     │ │                  │
 │     ╱   12.04 px   ╲   │ │  │▌▌           │ │                  │
 │ ───┘                └─ │ │  │▌            │ │                  │
 └────────────────────────┘ └───────────────┘ └──────────────────┘
```

* **左邊那張圖把整張卡的語義講完**：判準是什麼、邊被判在哪、為什麼是這個數字。
  **參數面板存在的目的，是讓這張圖看起來對。**
* 中間那張是粗糙度**的圖**，不只是一個 σ —— 頸縮發生在結構的哪一段看得到。
* 資料從 `ctx.meta["cd"]` 來（同 `GlvInspector`），所以**選到卡片的那一刻就有
  東西**，不是跑完一批才有。
* 量不到的時候摘要那一行比任何圖都有用，而它跟警告訊息**共用同一張對照表**
  （`cd.reasons_in_words`）—— 兩份的話畫面上講的原因會跟警告裡的是兩套說法。

## 9. 不在這一輪

* **無方向那一支**（Feret / 等效直徑 / 真實覆蓋面積）—— 第二批。界線已定：
  門檻切割只在區域內、不產生具名區域。
* **任意角度的掃描線**（非 x/y）。需要重採樣插值，而那會動到 LWR 的意義。
* **一格一格量**（`roi_template` 在大圖上鋪 625 個框 → 每格一個 CD →
  typical / outlier）。機制在 `glv_stats._measure_each_box` 已經有先例。
* **pattern-frame ROI**。合成 patch 上量到的線寬是雙峰的（6.5 / 22.5），因為
  patch 以缺陷為中心裁切、晶格相位逐顆不同 —— 而那正是 `algo/period` 的
  `estimate_period` / `choose_origin` 留著的理由（`CLAUDE.md` §5 的便利貼）。
* `lot baseline`（跨顆比較、離群旗標）—— 引擎還沒有那一層。
