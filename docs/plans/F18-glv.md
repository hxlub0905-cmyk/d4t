## 3. 心智模型：`method` 二選一 → 三個獨立的維度

現在使用者要先決定 `method = stats / compare`，而**這兩個 method 連接線方式
都不一樣**（清單埠 vs 角色埠）。對製程工程師，那是「還沒開始量，就先被問了
一個關於軟體架構的問題」。

改成三個彼此獨立的問題，順序就是他腦裡的順序：

```
① 在哪量？   region(s) × stream(s)      ← 畫布上的線
② 量什麼？   metrics（勾選）             ← 絕對值，永遠吐
③ 跟誰比？   reference（可以不比）        ← 相對值，追加在絕對值之上
```

**`compare` 不是另一個 method，是 `reference ≠ none` 的情況。**

這一刀解掉現在最實際的坑：現行 `compare` **從不輸出絕對值**，所以「這塊 EPI
的平均灰階是 120」跟「它比隔壁亮 12」不能在同一張卡上同時得到 —— 使用者得放
兩張卡、接兩次線，而那兩張卡各自有機會設得不一樣。

### 3.1 `reference` 的選項

| 值 | 意思 | 多長出什麼埠 | 誰在用 |
|---|---|---|---|
| `none`（預設）| 只要絕對值 | — | 兩種資料都常用 |
| `another region` | 同一張圖的另一塊（背景、鄰近 cell）| 一個菱形埠 | RSEM 大圖主力 |
| `another stream` | 同一塊在另一條流上（test vs ref）| 一個影像埠 | **patch 主力** |
| `the other regions` | 這一組同類區域的分布 → robust z / 排名 | 不用多接線 | RSEM 上千個區域時的正解 |
| `lot baseline` | 整批的中位數（two-pass）| 不用接線，**要動引擎** | 排最後，見 §8 |

前四個都只吃「現在這一顆」的資料 —— 所以**儀表在預覽時就畫得出來**，那正是
§4 成立的前提。

### 3.2 埠會隨參數變形，這**不是**新機制

`resolve_reads` / `resolve_regions_in` 本來就是 param-dependent（現行的
`method` 也是這樣改埠的）。差別只在**使用者要理解的東西變少**：主埠永遠在，
參考埠只在「你說你要比」的時候才長出來。

`tests/test_ui_f10_canvas_reality.py` 的 `ROLE_PORTS` 那條不變量要跟著改：
現在鎖的是「兩種接線方式各自合法、而且不同時出現」，之後鎖的是
「參考埠只在 `reference != none` 時存在」。

### 3.2.1 落地時多學到的一條（2026-08-21）

計畫說「參考埠只在 `reference != none` 時存在」，而
`tests/test_ui_f10_canvas_reality.py` 原本的 `ROLE_PORTS` 還鎖著一條更強的話：
**「不准混用清單來源與角色埠」**。新設計是**故意混用**的 —— 主埠是清單
（`source` / `roi`：多連一 = 同一件事量在好幾條流／好幾塊上），參考埠是單數
（一次只跟一個東西比）。

那條舊規矩不是白寫的，它防的是「**同一個**概念輸入有兩種形狀」；現在兩個埠
是兩個不同的問題、兩個不同的名字、而且參考埠只在使用者說要比的時候才出現。
所以 `ROLE_PORTS` 清空，改成一條新的不變量：
`test_the_reference_ports_are_singular_and_only_show_when_asked`。

### 3.3 遷移（鐵則 9：只能靠「舊東西在不在」判斷）

舊 recipe 的 `method="compare"` 還在 → 轉成
`reference="another region"`（或 `another stream`，看 `reference_source` 跟
`target_source` 一不一樣），四個角色參數搬過去：
`target_source`→`source`、`target_region`→`roi`，`metrics` 補成 `stat`
（舊卡片用那個統計量代表每一塊，所以「它的絕對值」正是使用者心裡的那個數字）。
做完把 `method` 刪掉，所以走第二次是 identity。

更舊的 `roi_compare` 節點先被 `_migrate_roi_compare_into_glv_stats` 變成
`method="compare"`，**再走這一道** —— 兩道的順序在 `from_json_dict` 裡是寫死的，
反過來的話那些節點會漏掉第二段。
**不能**用「新的 `reference` 鍵不在」來判斷 —— 那分不出「舊檔」與「新 recipe
吃新預設」，而 `to_json_dict → from_json_dict` 是 `run_batch` 送 recipe 進
worker 的路，它一旦不是 identity，`workers=1` 與 `workers=2` 會算出不同的分數。

## 4. Metrics 的 UI：分群的膠囊晶片，每顆帶一個「它在分布上是哪一段」的小圖

現在是 `MultiChoicePicker`（一欄三格的勾選網格，選項名是 `glv_q90` 這種
recipe 鍵）。它解掉了「用打的」那個問題（2026-08-14），但它長得像一張報稅表。

### 4.1 定案的樣子（mockup 已用專案的 theme token 真的畫出來）

```
Statistics                          4 picked · hover a chip to light it up
        ┌──────────────────────────────────────────────────────────┐
        │  min          −MAD median +MAD                       max │   ← 預覽帶
        │   ╷         ▁▃▅█▇▅▃▁    ▁▃▂▁                          ╷  │
        │ 0 ╵                                                  255 │
        └──────────────────────────────────────────────────────────┘
Center   (◔ Median)  ( Mean )  ( Trimmed mean )
Spread   (◔ MAD )    ( Std dev )  ( IQR )  ( p90−p10 )
Ends     (◔ Min )    (◔ Max )  ( + Percentile )
Shape    ( Skew )  ( Kurtosis )  ( Entropy )  ( Bimodality )
Counts   ( Above threshold )  ( Saturated % )
         →  epi_glv_median, epi_glv_mad, epi_glv_min, epi_glv_max
```

五件事讓它對「不會寫 code 的製程工程師」成立：

1. **分群**（Center / Spread / Ends / Shape / Counts）—— 十六顆平鋪是一面牆；
   分群之後使用者只要先決定「我要問的是中心還是離散」。
2. **每顆晶片一個小圖**，共通語言是
   **「淡的那條線是分布本身，實的那一筆才是這個統計量在講的東西」**：
   median 是把面積切一半的線、mean 是天平的支點、MAD 是中位數兩側的一段、
   std 是一對箭頭、IQR 是箱形圖的箱子、bimodality 是兩座山中間的谷。
   十六顆的差別**只在實的那一筆標在哪** —— 而那正好就是這些統計量彼此唯一的
   差別。使用者不需要知道 MAD 的定義，他看得到它在圖上是哪一段。
3. **預覽帶**：這一顆的真實直方圖，把勾選到的統計量**標在上面**。
   hover 一顆晶片，對應的標記亮起來。這是「量在哪裡」原則在**統計量**上的
   版本（一張大的誠實的圖 > 十六張小的模稜兩可的圖 —— 兩者我們都留，因為
   小圖負責「認出來」，大圖負責「看懂」）。

   ⚠ **落地時它搬到了儀表（第 2 步），不在設定區。** 理由不是工程方便：
   設定區（`ParamForm`）拿不到引擎算出來的東西 —— 它只有參數。要在那裡畫一條
   分布，只能畫一條**假的**，而「畫面不能說謊」是這個 repo 花了六個坑換來的
   規矩。儀表那邊本來就吃 `ctx.meta`，那才是它的家；hover 晶片 → 儀表上的標記
   亮起來，跨面板連動由 Studio 轉一手。
4. **`→ epi_glv_median, …` 那一行**：勾選會變成哪幾個 feature 名。
   那些名字會被打進分數表達式，所以它們不能只活在文件裡。
5. **`Percentile` 是一個動作不是一個統計量** —— 所以它的圖示是 `+`，
   按下去長出一顆可調的 `p__` 晶片，而不是要使用者打 `glv_q37`。

### 4.2 兩個備選（都畫出來了，取 C）

| | 內容 | 判斷 |
|---|---|---|
| **B** | 純文字膠囊 + 預覽帶 | 乾淨，但十六顆一樣的膠囊在掃視時沒有錨點 |
| **C ✅** | 帶小圖的膠囊 + 預覽帶 | 小圖給了錨點，而且它**教**了一件事 |

### 4.3 實作上的形狀

* 新 widget `MetricChips`（`ui/widgets.py`），對應新的 param 型別
  `metric_chips`。**值仍然是逗號分隔字串 —— recipe JSON 一個字都不用改**
  （同 `image_keys` 當年的做法）。
* 小圖走 `draw_metric_glyph(p, name, size, color, dim)`，跟
  `draw_group_icon` / `draw_glyph_icon` 同一條路：QPainter 畫、顏色吃呼叫端給
  的值（換膚自動跟著）、repo 不放圖檔。
* 驗收比照 F17 剛加的那一條：**十六顆兩兩至少差一成畫素**
  （`test_every_metric_glyph_is_a_different_shape`）。19 px 下量，因為晶片裡
  是 18–19 px —— 會先在小的這一邊糊掉。
* recipe 帶進來、不在清單上的值（手寫的 `glv_q37`）照樣列出來並勾著。
  看不到就被靜靜刪掉，是最糟的一種「幫忙」（`MultiChoicePicker` 已經有這條，
  不要弄丟）。

## 5. 預設換成 robust

e-beam 影像有 charging、hot pixel、掃描條紋 —— `mean/std` 是最脆的一組。

| | 現在 | 之後 |
|---|---|---|
| 預設 | `glv_mean,glv_std,glv_p50` | `median, mad, min, max` |

⚠ **動手之前先確認 `to_json_dict` 有沒有把參數全存下來。**
全存 → 舊 recipe 不受影響，只有新卡吃新預設。
沒全存 → 舊檔會**安靜地換一組數字**，那就得走 §3.3 的遷移路。

## 6. 「量得準不準」的三個旋鈕（現在完全沒有）

不改變量什麼，只決定**哪些像素算數**：

| 參數 | 做什麼 |
|---|---|
| `exclude_saturated` | 0 / 255 貼底貼頂的像素不算 |
| `trim_percent` | 兩端各去掉 n%（對付 hot pixel）|
| `min_pixels` | 樣本數低於這個 → **吐 NaN + 原因**，不是硬算一個 std 出來 |

配套輸出（每個區域都吐，跟 Region-4 的五個數字同一種契約）：
`<region>_n_px`、`<region>_saturated_frac`、`<region>_ok`。

**patch 的 ROI 常常只有幾百個像素，n 少的時候 std 本身沒有意義** —— 而現在
畫面上沒有任何地方講這件事。

### 6.1 落地時改了三件事（2026-08-21）

**① 「失敗吐 NaN」被 repo 自己的守門測試否決了 —— 而它是對的。**

計畫寫「量不出來就吐 NaN，不要吐 0」。做完之後
`tests/test_card_invariants.py` 的 I5 紅了，訊息是：

> 產出了 NaN／Inf 的特徵 —— score 會跟著變 NaN，而 `NaN < threshold` 是
> False，那顆 defect 會**安靜地被判成真缺陷**

也就是說 NaN 比 0 更糟，因為它看起來比較誠實。三種都想過：

| 寫什麼 | 下場 |
|---|---|
| `0` | 進得了分數表達式、寫得進 DSIZE，一路安靜到最後（`cd_x_nm` 就是這樣咬過一次的）|
| `NaN` | 上面那條 —— 安靜地判成真缺陷。要先有 ADC 段的 NaN 政策（F19）才輪得到它 |
| **不寫** ✅ | 沒有人引用 → 什麼都不會發生；**有人引用 → 那顆 defect 當場失敗，訊息裡帶著變數名** |

所以量不出來的時候那幾格**不寫**，而 `glv_ok`（值 0）照寫 —— 分數表達式因此
有一個乾淨的分支點。不能用 raise：鐵則 7（單顆出錯不得殺掉整批）。

**② `<region>_n_px` 改名 `glv_pixels`。** 以 `_px` 結尾的特徵會被 nm 孿生規則
自動配一個 `_nm`（`_util.nm_twin_names`），而「幾個像素」換算成奈米沒有意義。
這一格是個**數量**，不是長度。

**③ `saturated_frac` 不另外吐。** 它已經是一顆晶片（`glv_sat_frac`），而診斷用
的那一份在 `ctx.meta` 裡（面板讀它）。同一件事有兩個出處就會漂 —— 這份計畫書
第 0 節講的就是這個。

⚠ **`glv_pixels` 讓每一張 Gray level 卡多一個特徵**，所以
`tests/fixtures/golden/` 的特徵名集合對不上了（值一個都沒動）。
`D4T_GOLDEN=1` 那把尺會報「多了 glv_pixels」——
**在你自己的機器上重跑一次 `python tools/freeze_golden.py`**（這個容器算出來的
浮點數跟你那台不一樣，在這裡重凍等於把你的基準洗掉）。

## 7. 儀表：Spread 出去，「這一顆的分布」進來

```
┌─ Gray level ─────────────────────────────── n=842 px · 0.4% sat ─┐
│                    ▁▂▅█▇▃▁          ▁▃▅▄▂                        │
│  epi ───────────────╫──┼──────────────────────  median 118.3     │
│  mg  ┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈╫┈┼┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈  median 141.0     │
│      0        64       128       192      255   Δ = +22.7 (z=3.4)│
│  ▏this defect in the batch▕ ▔▔▔▔▔●▔▔▔▔▔▔▔▔▔▔▔   ← 跑過才出現的細帶 │
└──────────────────────────────────────────────────────────────────┘
```

* **主體是這一顆的直方圖**，一個區域一條，顏色跟影像上的疊框、模板編輯器
  同一組（`theme` 已經有那組色）。**預覽就有，永遠不空。**
* 勾選到的 metric 直接標在圖上（跟 §4 的預覽帶是**同一段繪圖程式**）。
* 有 reference 時兩條分布疊著畫，差異寫在右邊 —— 「亮了 22.7 階」跟「疊在一起
  差這麼多」是同一件事的兩種說法，使用者需要後者才信前者。
* 整批的資訊縮成底下一條 8 px 的帶子（這一顆在整批的哪個百分位）。跑過才出現，
  但它只是一條帶子，不是整塊面板。

資料一律**來自引擎算的那一份**（`ctx.meta`），UI 不自己重算一次 ——
不然畫面上的曲線跟真的跑出來的有機會不一樣（`inspectors.py` 檔頭的第 2 條）。

### 7.0 落地了什麼（2026-08-21）

* 引擎：`glv_stats._note_distribution` 往 `ctx.meta["glv_hist"]` 留每一塊的
  64-bin 直方圖 + 樣本數 + 飽和比例 + 勾到的統計量的值。**畫面上那張圖就是
  引擎算的這一份**（同 Enhance 的 `stream_change`）。
* `MultiSourceStep` 多兩個內部鍵 `_stream` / `_prefix`：子類刻意不知道「接了
  幾條流」，但要往 meta 留東西就得說得出「這一份是誰的」。
* `GlvInspector`：一塊一條直方圖（顏色跟影像上的疊框同一組），勾到的統計量
  **用它自己的形狀**標上去 —— 見下面那條規矩。整批縮成底下一條 8 px 的帶子。
* 其餘量測卡**暫時留在 Spread**：它們還沒有自己的面板，而沒有面板比
  「跑完才有東西的面板」更糟。CD 那張本來就要整張重做（F19）。

### 7.0.1 最容易說謊的地方：三種統計量在灰階軸上不是同一件事

| | 是什麼 | 怎麼畫 |
|---|---|---|
| median / mean / trimmed | 一個**位置** | 整條實線 |
| min / max / p<NN> | 一個**位置** | 貼著底的短刻度 |
| MAD / std / IQR | 一個**寬度** | 中心兩側的一段淡帶 |
| skew / kurtosis / entropy / bimodality / saturated | 單位不是灰階 | **不畫**（值在特徵表上）|
| above<NN> | 值不是灰階，但**門檻是** | 門檻畫成虛線 |

第一版把每個勾到的都畫成一條線，於是 `glv_mad = 65` 在灰階 65 畫了一條線 ——
那裡什麼都沒有。寬度沒有中心可以掛的時候（只勾 MAD、沒勾中位數）**不畫**：
「這個數字沒有畫得出來的位置」是一個誠實的答案。
`tests/test_ui_f7_17_inspectors.py::test_a_width_statistic_is_not_drawn_as_a_position`
用畫素比對鎖住這三條。

### 7.1 Spread 搬去哪

它回答的是 **「這個特徵分不分得開、門檻該設哪」** —— 那是 ADC 與 Results 的
問題，不是量測卡的問題。

**定案：Results 面板的特徵分布視圖** —— 列出所有 feature、點一個看分布。

落地時多了一條**沒有寫進計畫、但不寫就會出錯**的規矩：
**門檻是「分數」的門檻，所以看別的特徵時整張圖是唯讀的。**
原本的計畫寫「直接在分布上拖門檻」—— 在 `glv_median` 的分布上拖門檻會拿一個
跟畫面無關的值改掉 bin，那是這個 repo 反覆在避免的「跑得完、有反應、而且是
錯的」。改成：分數 → 門檻拖得動（照舊）；別的特徵 → 唯讀，畫一條
**這一顆在哪裡**的標記線，外加一句「這個特徵分不分得開」。

下拉列的是**真的算出來的**那些（從 `trial_results` 讀，不是從 recipe 宣告
讀）—— 宣告會產出但那一輪沒算出來的名字，選了只會得到一張空圖。

## 8. patch（小圖）vs RSEM（大圖）：同一張卡，兩種閱讀方式

### 8.1 計畫寫的是「接了幾個區域」，而資料模型不是那樣（2026-08-21）

計畫這一節假設 RSEM 上會接到「幾百到幾千個區域」，然後靠**區域的數量**自動
切換成聚合模式。做的時候去看了資料模型，那個前提是錯的：

**一個名字底下就是好幾個框。** `roi_from_mask` 的一層是**一個**名字（`epi`）
配上幾千個矩形；`roi_template` 在 1000×1000 上鋪出 625 個框，也都掛在同一個
名字下。所以「幾百個單元」從來不是幾百個區域，而是**一個區域的幾百格**，
而 `roi_pixels` 一直是把它們接成一個像素母體（F8 多框區域本來的用途）。

換句話說，該切換的不是「接了幾個區域」，是「這個區域裡的框要**一起**量還是
**一格一格**量」。那是一個使用者答得出來的問題，所以它是一個參數
（`across_boxes`），不是一條猜出來的規則。

### 8.2 落地的樣子

| `across_boxes` | 答的問題 | 誰在用 |
|---|---|---|
| `pooled`（預設）| 「這一整組交界長什麼樣」 | patch 的 F8 交會區域 |
| `each box` | 「**哪一格**跟別人不一樣」 | RSEM 的重複單元 |

一格一格量之後，每個數字變成三個（外加一個 `boxes` 說總共量了幾格）：

| | 是什麼 |
|---|---|
| `<n>_typical` | 每一格算完之後的**中位數** —— 這一批單元長什麼樣 |
| `<n>_outlier` | 離 typical 最遠的那一格的值 |
| `<n>_outlier_box` | 那是第幾格（0 起算）—— **缺陷定位的答案** |

* **不逐格吐特徵**：框的數量隨影像而異（換一顆 defect 就不一樣），逐格吐的話
  recipe 得寫死一個不存在的數量，CSV 也會多出幾千欄。
* **「跟誰比」也一格一格算**（參照那一塊是共用的），所以 `delta` 那幾個吃同一
  套後綴 —— 「跟隔壁材質比，哪一格最不一樣」只有在這個模式下答得出來。
* **太小的格子跳過，不是寫 0**：框是鋪出來的，壓在影像邊上只剩幾個像素是正常
  的，而它的統計量會把 typical 拉走。`boxes` 說得出真正量了幾格。
* **面板畫的是「典型那一格」**，並且說出那是第幾格 —— 把幾百格疊起來畫等於畫
  一張什麼都看不出來的圖。

⚠ **兩個名字是我定的，不是使用者定的**：`_typical` / `_outlier`（計畫書原本寫
`med` / `p95` / `worst`）。理由是讀它們的人是製程工程師，這兩個詞不必查就懂；
而 `p95` 被拿掉是因為「典型」與「最不一樣的那一格」已經是這個問題的全部，
第三個分位數只是多一欄。要改成別的字很便宜（三個常數 + 一份測試）。

## 10. 落地順序（每一步都能單獨驗收）

| 步 | 做什麼 | 動到引擎嗎 | 黃金值會變嗎 |
|---|---|---|---|
| 1 ✅ | `MetricChips` + `draw_metric_glyph` + **引擎的統計量** + robust 預設 | ✅ 小（純新增）| ❌ |
| 2 ✅ | 儀表換成「這一顆的分布」；Spread 搬去 Results | ✅ 只多寫一份 meta | ❌ |
| 3 | robust 預設（含 §5 的確認）| ✅ 小 | ⚠ 要先確認 |
| 4 ✅ | §6 的三個旋鈕 + `glv_pixels` / `glv_ok` | ✅ 小 | ⚠ 特徵名多一個，見 §6.1 |
| 5 ✅ | `reference` 維度取代 `method`（含遷移）| ✅ 中，動埠 | ❌（相對值的名字逐字不變）|
| 6 ✅ | 一格一格量 + 聚合（RSEM）| ✅ 中 | ❌（預設 pooled，等於沒開）|

### 10.1 第 1 步實際做了什麼（2026-08-21）

計畫寫的是「第 1 步純 UI」，落地時**把引擎那一半一起做了**，而那不是範圍蔓延：
晶片上列得出來的每一顆，引擎都要真的算得出來 —— 只做 UI 的話那是一排按了
沒事的鈕，比原本的勾選網格更糟。

* `algo/glv.py`：新增 `glv_mad` / `glv_iqr` / `glv_skew` / `glv_kurt` /
  `glv_entropy` / `glv_bimodality` / `glv_sat_frac`，以及兩種帶數字的 id
  `glv_trim<NN>`（兩端各去 NN%）與 `glv_above<NN>`（灰階高於 NN 的比例）——
  形狀跟既有的 `glv_q<NN>` 一模一樣，因為多一種語法就是多一種打錯的方式。
* **每一顆都有防呆**：整塊同一個值（飽和的 patch 上很常見）與空的 patch 一律
  回 0.0，不回 NaN。一個 NaN 進了分數表達式就是「跑得完、有數字、而且是錯的」。
* `ParamSpec` 多一個型別 `metric_chips`（正規化與 `multi_choice` 共用同一段，
  值的格式一字不差）。
* 預設換成 `glv_median,glv_mad,glv_min,glv_max`，並補上一條測試鎖住
  「預設會被寫進 params」這個前提 —— 那正是換得掉的原因。
* 三支既有測試跟著改：兩支拿預設值當前提（改成明寫 `metrics`，因為它們測的是
  快取與多入口，不是預設值），一支問 `epi_glv_mean`（改問 `epi_glv_median`，
  它測的是**前綴**）。

第 2 步（儀表換成「這一顆的分布」、Spread 搬去 Results）不動引擎、不動 recipe、
黃金值不會變 —— 而它是使用者說「跑完才有」那一句的正解。

## 11. 這一輪要守住的既有不變量

1. `d4t/core` 不得 import Qt；小圖住在 `ui/widgets.py`，**卡片只宣告參數型別**。
2. 每個 ParamSpec 的 `help` 必填、要白話；晶片的標籤是 `label`，
   **`name` 仍然是 recipe 的鍵**。
3. 吃影像流／區域的參數一律 `image_key(s)` / `region_key(s)`，設定區唯讀 ——
   來源只在畫布上拉線決定。
4. 遷移只能靠「舊東西在不在」判斷（鐵則 9）。
5. 卡片數量不能爆：§4 列的十六個量全部收進**一張卡的一個參數**，
   不是十六張卡（F7-10／F7-20 的慣例，也是推廣鐵則）。
