# F120 — Pitch helper（丟一張圖進去，回答它的 cell period）

狀態：**第八版，等使用者看過（2026-09-21）** —— `python -m d4t pitch` 開得
起來，四點追加的需求都在（§5／§5.1／§5.2），使用者七輪回饋都做完（§18），
第八輪是「截其他狀態的圖」而那幾張圖抓出三個 bug（§19）。⚠ **不寫「已收斂」**：使用者還沒
在真實影像上用過，而這種工具的驗收只有那一件事算數。⚠ §5 那顆「格線」按鈕
**做的時候從「一顆鈕」改成「預設開著」**，理由與它揪出來的那個 bug 在 §10。

使用者 2026-09-21 指定：把「算 repeating pattern 的 cell period」這一件事
**獨立成一個 helper**，原本 ROI 那張卡的功能一個字都不動。形狀照 `simgen`
（自己的 CLI 進入點 ＋ 獨立小視窗）。同一天追加四點：**要能看圖驗證**、
**cell 切點格線預覽**、**純 X／純 Y 也要支援**（今天是 X＋Y 都取最小週期成
GC）、**原有的 crop 也要有**。

---

## 1. 為什麼

使用者的原話：

> 主要是算 Golden cell（應該在 ROI 內那張卡），命名就叫 **pitch helper**，
> 主要功能就是丟一張圖進去，算 repeating pattern 的 cell period
> （可支援 pixels & X(nm)）。

今天這個能力**只存在於一條很長的路的中間**：Studio → `roi_reference`
（`method="template"`）→ `TemplateDialog` → 匯入大圖 → 疊模板。週期是那條路的
**副產品**，而使用者常常只想要那個數字本身 —— 他手上有一張 SEM，他要知道
pitch 是多少。為了那一個數字，今天他得先開 Studio、先有一份 recipe、先加一張
ROI 卡、先接好線，才點得到那個對話框。

**那不是「功能不存在」，是「入口不存在」。** 所以這一份不新增任何演算法。

## 2. 不做什麼（範圍）

* **不動 `roi_reference` / `roi_template` / `TemplateDialog`。** 原功能原封不動，
  黃金值不動、recipe 不動、卡片庫不動。
* **不疊 Golden Cell。** 疊圖（`build_golden_cell`）在 7680² 上要十幾秒，而它
  回答的是「模板長什麼樣」。helper 回答的是「pitch 是多少」，那是
  `template.measure_period` 一支就答得完的事。
* **不猜 nm/px。** 見 §4。

## 3. 核心邏輯不搬家、不抄第二份

量週期的**唯一出處**是 `algo/template._measure_period` —— 三票制（投影法
`period.estimate_period` ＋ 二維自相關 `period2d.estimate_period_2d` ＋
半週期檢查 `period2d.half_period_check`），四個月的實測、諧波修正、交錯晶格的
加倍規則全部長在它身上。

它今天是**私有**的，而 helper 需要一個講得出口的入口。所以：

> `_measure_period` → **`measure_period`**（公開，進 `__all__`）。

⚠ **不留舊名字的別名。** 一件事兩個名字正是 `CLAUDE.md` §0 在擋的東西；
呼叫者只有三處（`build_golden_cell` 一處、兩支測試各一處），一起改。
這一步**不改任何一行演算法**，驗收是 `freeze_golden.py --check` 三份逐項相同。

## 4. 單位：px 是答案，nm 是換算（照既有的那條規矩）

`docs/FAB-VALIDATION.md` 的假設 #2 已經定調：**`nm_per_px` 在 KLARF 裡沒有
來源，所以單位一律 pixel、換算搬到輸出那一刻**。`algo/grid.py` 的檔頭把這件事
講得更白：「這裡收 nm 的話，它會變成第二個恆為 0 的 `cd_x_nm`」。

helper 照抄卡片那一套（`steps/_util.nm_per_px_spec`）：

| | |
|---|---|
| **Pixel size** 一格，單位 nm/px，**預設 0 ＝ 不知道** | 使用者自己填（機台設定裡有） |
| 0 的時候 | 只顯示 px。**不顯示一個 0 µm** —— 那看起來像一個量出來的答案 |
| > 0 的時候 | px 底下**同時**顯示 µm（`period × nm_per_px / 1000`），兩個都在 |

⚠ **進去是 nm/px，出來是 µm**（第七輪改的，使用者原話：「pixel size 換算後，
單位改成 um（px 輸入一樣是 nm）」）。兩邊單位不同不是不一致，是**兩邊各自的
量級**：pixel size 是個位數的 nm，而一個 cell 的 pitch 是幾百個 nm ——
`1,200 nm` 要數逗號，`1.200 µm` 不用。

換算本身是一個乘法，所以它住在畫面那一層；core 不會多一個 nm 的概念。

## 5. 「假設算不對我該怎麼知道」

這是使用者 F103 問過的那一句，而它對一個**只輸出一個數字**的 helper 更尖銳：
一個錯的 pitch 看起來跟對的一模一樣。所以畫面上要有三層證據，而它們都已經
存在，只是搬進同一個視窗：

1. **每一軸的信心值**與 `measure_period` 的 `notes`（換了量法、加倍了、
   諧波鏈不直 —— 每一句都是使用者該知道的決定）。
2. **交錯分數** `stagger`（交錯晶格 ≈ 1、規則晶格 ≈ 0）。
3. **把 cell 的切點格線鋪回原圖**（`lattice_dialog.lattice_boxes`，F103 那一套）
   —— 「每一格框住的東西都一樣就是對的；格線在圖的另一頭漂到別的結構上，
   就是錯的」。一眼的事，不需要懂任何分數。

⚠ **格線預設開著，不是一顆要去找的按鈕**（使用者 2026-09-21 追加：「要能驗證
（看圖）」「cell 切點格線預覽」）。代價是量完之後還要跑一次
`period.choose_origin`（相位搜尋，4096² 實測 5.3 秒）—— 所以它跟量週期**在同一
個 worker 裡一起跑完**，進度條講到哪一步，而不是量完先還一個數字、再讓使用者
按第二顆鈕等第二次。留一個開關是為了「看原圖」，不是為了省那幾秒。

### 5.1 純 X／純 Y（使用者 2026-09-21 追加）

> 「也能支援純 X 純 Y（目前是 X+Y 都取最小週期成 GC）」

一維的 layout 是常態（垂直條紋只有 X 有週期），而自動判斷會在**兩軸都量得到
東西**的時候兩軸都切 —— 使用者要的那個單元卻可能只在一個方向上重複。所以
軸向是一格**使用者說了算**的選擇，四選一（`chip_choice` 的膠囊形狀）：

| 選項 | 意思 |
|---|---|
| **Auto** | 量到哪一軸就用哪一軸（今天的行為，預設） |
| **X only** | 只切直線。Y 那一軸「一格就是整張影像」（`lattice_boxes` 本來就這樣處理沒有週期的軸）|
| **Y only** | 只切橫線 |
| **Force both** | 兩軸都切，**即使某一軸信心不足**（使用者明講的一律相信 —— 同 `build_golden_cell` 的 `given` 規則）。⚠ 原本叫 `X + Y`，第七輪改名，理由在 §18.4 |

⚠ **它不改量出來的數字**，只改「哪幾軸算數」。兩軸的 px／py 一直都量得到。

~~選 X only 只是讓 Y 那一欄變成「not used」而不是消失 —— 藏起來的話使用者會
以為量不到。~~ → **使用者 2026-09-21 推翻了這一條**：按下 X only 的人是自己
按的，他知道 Y 還在，那一列對他只是噪音。現在**整列不顯示**，見 §15.2。

### 5.2 Crop（使用者 2026-09-21 追加：「原有的 crop 功能也要有」）

直接用 `ui/crop_dialog.CropDialog` ＋ `crop_array` —— **同一支**，不抄第二份。
它存在的理由在 helper 上一字不差地成立：整張圖裡不只有你要的那種 cell
（缺陷本體、scribe line、機台的量測條），而週期估測看的是整張圖的投影。

兩處接法：

* **載入一張圖之後**跟著問一次（同 `template_dialog`「每次載入大圖都會出現」）；
* 畫面上一顆 **Crop…** 鈕，隨時回去改那一塊，改完自動重量。

⚠ `CropDialog` 的 OK 鈕今天寫死「Stack from this box」（模板那條路的字）。
helper 不疊圖，所以那句話在這裡是假的 —— 加一個 `ok_text` 參數，**不分叉出
第二個對話框**。

## 6. 跑在背景執行緒

實測（這台容器，合成圖）：

| 影像 | `measure_period` | `choose_origin` |
|---|---|---|
| 512² | 160 ms | 113 ms |
| 1024² | 912 ms | 367 ms |
| 2048² | 1.7 s | 1.1 s |
| 4096² | 2.8 s | 5.3 s |

超過一秒的東西跑在 UI 執行緒上，視窗會被 Windows 標成「沒有回應」——
`build_golden_cell` 的 `progress` callback 當初就是為了這件事加的。所以
helper 用 `QThread` worker（形狀照 `gc_generator._GenWorker`）。

## 9. 驗收

* `python -m d4t pitch` 開得起來，丟一張合成的週期圖進去，量到的 pitch 與
  產生它的參數相同；
* 填 nm/px 之後 nm 那一欄出現，填回 0 就消失（**不是變成 0 nm**）；
* 量完**自動**畫出切點格線，格子落在同一種結構上；
* 軸向選 X only 時只切直線，**Y 那一列整列不顯示**（§5.1 原本寫的是
  「寫 not used」，使用者 2026-09-21 推翻了 —— 見 §15.2）；
* Crop 之後重量，量到的是那一塊的週期（用一張「左半邊 40 px、右半邊 24 px」
  的合成圖驗：不裁跟裁一半要給出不同的答案，否則那顆鈕是裝飾）；
* `freeze_golden.py --check` 三份逐項相同（§3 的重新命名沒有動到任何數字）；
* `ruff check` 綠、核心批綠、新測試綠。

## 10. 做的時候改掉的事，與預覽揪出來的那個 bug

**§5 的「格線是一顆按鈕」撤回了。** 使用者追加「要能驗證（看圖）」「cell 切點
格線預覽」之後，那顆鈕的前提就不成立了：要人**去找**的驗證等於沒有驗證。
所以格線跟量週期在同一個 worker 裡一起跑完、預設開著，勾勾留給「我要看原圖」。

**預覽揪出一個真的 bug（已修，有回歸測試）。** 第一版按下「X only」之後：

* 表格**立刻**寫 `Down (Y) — not used`；
* 而圖上的**橫線還在**，因為重畫排在 `choose_origin` 後面，要等好幾秒。

畫面同時在說兩件相反的事，**而使用者會相信圖**。修法是軸向一改就當場用舊的
原點重畫（丟掉 Y 軸不會改變 X 的相位），worker 回來再換成重新搜出來的那一個。
守門：`test_ui_pitch_helper.py::test_switching_the_axis_redraws_the_grid_at_once`。

⚠ **那是「畫一張圖看看」買到的，不是讀程式碼讀出來的。** 兩段程式各自都正確
——表格讀的是同步算得出來的 flags，格線讀的是非同步回來的 origin；錯的是
它們**在同一個畫面上**，而畫面沒有「稍等」這個狀態。

**`measure_period` 多了一道空影像的防呆。** 它私有的時候不需要（唯一的呼叫者
更早就擋掉了），公開之後呼叫端是「使用者剛剛丟進來的那個東西」，而
`cv2.Sobel` 對 0×0 是 `cv2.error`。**開放一支函式就要讓它自己站得住。**
驗過 `freeze_golden --check` 三份逐項相同 —— 那條路 `build_golden_cell` 走不到。

## 12. 使用者問的兩題（2026-09-21），與第 1 題逼出來的那一格

> **1. Pitch 算出來了，該怎麼證明他是對的而不是錯的？如果錯了怎麼辦？**
> **2. Confidence 怎麼算的？幾分以上才 OK？**

### 12.1 怎麼證明它是對的（三層，強度由弱到強）

| 證據 | 它回答什麼 | 它**不**回答什麼 |
|---|---|---|
| **信心值** | 「平移這個週期之後，圖跟自己有多像」 | 那是不是**你要的**那個單元。半週期的格子彼此也很像 |
| **notes** | 量的過程換過量法沒有、加倍過沒有、諧波鏈直不直 | 同上 |
| **格線鋪回原圖** | **每一格框住的東西是不是同一個結構** | —— |

**只有第三個是決定性的**，而這正是 F103 當初做格線檢視的理由（`lattice_dialog`
的模組說明）：數字回答的是「疊得齊不齊」，不是「週期是不是你要的那一個」。
所以格線在這個 helper 裡**預設開著**（§10），而不是一個要去找的開關。

⚠ **最容易出錯的那一種，數字看起來完全正常**：量到的是真週期的一半（或
你要的單元是兩個重複）。信心會很高、notes 什麼都不會說，而格線會**每兩格**
才對上你心裡那個單元 —— 那一眼看得出來，而分數看不出來。

### 12.2 如果錯了怎麼辦 —— 這一題原本**沒有答案**（F120 第二版補的）

第一版**只能看，不能改**。而 `template_dialog` 早就定了那句話：

> 「cell 多大由使用者決定：**量出來的週期是預設值不是結論** —— 例如兩根 MG
>  才構成他要比的那個單元。」

那句話在 helper 上**更成立**：這個視窗的唯一輸出就是那個數字，改不動它等於
「算錯了只能關掉視窗」。所以補上「**Use instead**」兩格 ＋ `×2` ＋ `Reset`：

* 打進去的週期**立刻重畫格線** —— 你打的那個對不對，當場用眼睛驗（同 §10 的
  那條：不能等相位搜尋回來）；
* 打進去的那一軸**跳過信心那一關**（使用者明講的一律相信，同
  `build_golden_cell` 的 `given`）；
* 信心那一欄改寫 **`you typed it`**。⚠ **不准沿用量出來的分數**：那個分數是
  對**它量到的**那個數字算的，掛在使用者打的數字旁邊等於拿一個他沒問過的
  問題的答案去背書他的輸入；
* 畫面上常駐一行「yours 120, it measured 60」—— **改過了一定要看得到**，
  否則換一張圖之後還掛著上一次打的數字，而沒有任何東西說那是他打的。

### 12.3 Confidence 怎麼算的，幾分以上才 OK

**兩條路算出來的是同一個東西**：那個週期上的**正規化自相關值 × 100**，
也就是「把圖平移一個週期，跟原圖有多像」（1.0 = 完全一樣）。

* 投影法 `period._analyze_axis`：`strength = 拋物線內插後的 ac 峰值`，
  clip 到 0–1 再 ×100；
* 二維自相關 `period2d._axis_period`：`conf = clip(v[p0], 0, 1) * 100`。

**門檻有兩道，而它們問的是兩件不同的事：**

| 門檻 | 值 | 誰在用 | 意思 |
|---|---|---|---|
| `period.estimate_period` 的 `strength_threshold` | **0.18**（= 18 分） | 投影法自己 | 低於它那一軸直接回「沒有週期」，連數字都不給 |
| `template.MIN_PERIOD_CONFIDENCE` | **40** | `build_golden_cell`、helper 的 **Auto** | 低於它的那一軸**當成沒有週期** |

**實測的刻度**（`build_golden_cell` 的註解與這一輪的量測）：

* **純雜訊 ≈ 20** —— 假週期就長這樣，所以 40 這條線是在擋它；
* **真的有週期 ≈ 87–98**（這一輪的合成圖是 92／93，4096² 的是 98）。

所以實務上的讀法：**> 85 放心；40–85 一定要看格線；< 40 它自己就不採用了。**
⚠ 但 §12.1 的那句話仍然成立 —— **高分不代表那是你要的單元**，半週期一樣拿
高分。分數答不了的那一題，只有格線答得了。

## 13. 版面重做（使用者 2026-09-21 第二輪的四點）

> 1. UI 跟 UX 介面我不喜歡（排版很怪）→ 理想上 user 進來是要 **1 min 內解決

>    **What it decided 這我不知道可以幹嘛？**

>    錯的話疊起來糊糊的。**所以要有一個 cell 的顯示放在附近。**
> 3. 信心分數跟上方整合，除了數字外**也要有視覺 UI**（橫向長條／綠黃紅）。
> 4. 我們現在是如何算 period 的？

### 13.1 版面：一條細工具列 ＋ 左圖右答案

第一版是**四個編號方塊由上而下**，每一塊都帶一段說明 —— 讀完才知道要按哪裡。

### 13.2 證明：疊起來那一格（使用者指定的做法）

走 **`build_golden_cell` 本人** —— 第一版只叫 `choose_origin` 自己畫格線，

ROI 卡在用的同一支；繞過它等於抄第二份。

畫面上因此是**兩張圖**：原圖＋切點格線、以及疊起來的那一格。實測（合成圖，
真實 pitch 60×44）：

| 情況 | 疊出來 | cells agree |
|---|---|---|
| 週期對（60×44） | 清楚的四格圖案 | **0.99** 綠 |
| 使用者打錯（37×29） | 一片灰糊 | **0.02** 紅 |

### 13.3 ⚠ 分數用 `agreement` 不用 sharpness —— 而這是量出來的

使用者的原話是「我們在用人眼，或是**算 sharpness** 這樣評估」。前半對，
後半 **F40（2026-08-26）量過，不行**：

`ghosting_score`（銳利度）只看疊完那一張圖，**看不到疊進去的那幾格**，所以
分不出「因為對齊了所以銳利」與「因為兩個鬼影各帶一組邊所以銳利」——
**相位錯掉的 stack 實測 76.1，而正確的只有 68.4**；純雜訊在 σ=60 拿 **99.4**。
它也不跨影像可比（跟著對比、雜訊、格子大小一起動）。

`golden.stack_agreement` 問的是那幾格**彼此**對得多齊：

```
a = var(mean(cells)) / mean(var(cell_i))     再扣掉 1/n 的地板
```

無量綱、跨影像可比，所以它才是那個可以配固定門檻的數字。綠燈的界線沿用
`template_dialog.BLURRED_BELOW` —— **同一件事不准有兩個門檻**。
守門：`test_sharpness_is_not_the_metric_and_here_is_why`（雜訊的 sharpness
> 50、agreement < 0.1）。

## 14. 我們現在是怎麼算 period 的（第 4 題）

`algo/template.measure_period(gray)`，**三票制**，全部在 `d4t/core/algo/`：

### 第一票：投影法（`period.estimate_period`）—— 主力

1. 兩軸各取一條**強度投影**（沿另一軸取平均），高通去掉照明梯度；
2. **調變閘**：投影的標準差 < 0.5 灰階 ⇒ 那一軸是平的，直接回「沒有週期」
   （條紋 layout 的另一軸就是這樣）；
3. **rFFT** 在自適應的 `[lo, hi]` 帶裡挑最強的峰 → 粗候選；
4. **正規化自相關** ＋ 拋物線內插 → 次像素修正，並仲裁基頻
   （強度頻譜的基頻佔優，避開梯度投影的「邊緣加倍」）；
5. **諧波修正**：`ac[2p] > 1.15·ac[p]` 就加倍、`ac[p/2] ≥ 0.9·ac[p]` 就折半。

### 第二票：二維自相關（`period2d.estimate_period_2d`，F104）

整張圖的二維自相關面，沿 X／Y 軸線取**離原點最近、夠高**的峰
（≥ 最高峰的 0.85 且 ≥ 0.3），再沿諧波鏈擬合**次像素**週期。
它在兩種情況接手（**兩票同意時整數不改，黃金值不動**）：

* 投影法那一軸量不到 —— 交錯 layout 的 X 軸就是這樣（相鄰列相位差半格，
  投影互相抵消）；
* 二維量到的是投影法的**整數倍** —— 投影看到的是半格的重複。

### 第三票：半週期檢查（`period2d.half_period_check`，F105）

比 `ac[2q]` 與 `ac[q]`：交錯晶格上平移 q 只對到一半、2q 才整個對上，
所以高出 `HALF_PERIOD_GAIN` 就**加倍**。使用者明講的軸不看。

### 收尾

`_snap`：離整數近到**整張圖漂不到半個像素**就回整數
（判準是漂移不是絕對值 —— 79.5×50 列 = 25 px 不 snap）。

### 然後才疊 Golden Cell（`build_golden_cell`）

小數週期先 `cv2.resize` 成整數 pitch → `period.choose_origin` **相位搜尋**
（≤256 個候選 ＋ ±2 精修，用疊出來那格的 Laplacian 變異數排序）→
`golden.stack_cells` 平均疊起來 → `ghosting_score` / `stack_agreement`。

⚠ **helper 把量到的兩個數字明講給 `build_golden_cell`**（`px=` / `py=`），
所以它不會再量一次 —— 量已經做過，而且使用者可能自己打了一個。

### 15.1 「差一點點」的實測 —— 兩個結論，一個推翻了我的設計

真實 pitch 60、900 px 寬（15 格），故意用不同的週期去疊：

| 試的 px | 誤差 | 整張圖累積漂移 | cells agree | sharpness |
|---|---|---|---|---|
| 60.0 | 0 | 0 px | **0.980** | 96.4 |
| 60.5 | +0.8% | 7.5 px | 0.912 | **39.1** |
| 61.0 | +1.7% | 15 px | 0.804 | **38.2** |
| 62.0 | +3.3% | 30 px | 0.633 | 42.1 |
| 63.0 | +5.0% | 45 px | **0.478**（紅）| **81.2** |
| 65.0 | +8.3% | 75 px | 0.392 | 82.4 |

**① `agreement` 單調下降，讀得出「差一點點」。** 圖上差 0.5 px 邊界就開始軟，
差 2 px 肉眼明顯。

**② ⚠ `sharpness` 在這個情境下是**非單調**的 —— 它會反過來騙人。**
差 0.8% 的拿 **39**，差 5% 的拿 **81**。**照 sharpness 排序會挑掉錯得更多的
那一個。** 這比 F40 原本那組數字更直接，所以釘成一條測試
（`test_sharpness_is_not_monotonic_on_small_errors`）。

**③ ⚠ 而 `agreement` 的解析度取決於那一軸放得下幾格 —— 這一條推翻了我原本
以為成立的假設。** 漂移 ＝ 誤差 × 格數：

| 影像 | 沿 X 的格數 | 65 px（差 8.3%）的 agree |
|---|---|---|
| 900 px 寬 | 15 | **0.39** 紅（對）|
| 300 px 寬 | **4** | **0.76 綠**（假的）|

所以**裁太小的時候那個綠燈信不過**，而那件事使用者看不出來 —— 畫面上就是一個
綠燈。新增 `cells_along` ＋ `trust_note`：格數少於 `MIN_CELLS_TO_TRUST`（8）
就在警告條講出來。

⚠ **這裡面還有一個我第一版寫錯的地方**（渲染的時候抓到）：我拿
`GoldenCell.n_cells`（＝ nx × ny）去比門檻，而 300×240 用 65×44 切是
4×5 ＝ **20 格** —— 看起來很多，但沿 X 只有 **4** 格。**拿總格數去判斷的話，
最該被警告的那張圖不會被警告到。** 判準改成**單軸最少的那個**。

### 15.2 做了什麼

| 項目 | 說明 |
|---|---|
| **候選一鍵套用** | `Or try [30×44] [120×44] …` —— 來自 `estimate_period` 本來就算好、以前算完就丟的 `candidates`。取錯幾乎永遠是取到諧波裡的另一個，所以這是「取錯怎麼辦」真正的答案（分數回答「為什麼」，候選回答「那我現在怎麼辦」）|
| **▸ Details（預設收起來）** | 三票各自的週期與信心。⚠ **不常駐** —— 同一輪使用者也說了「不要看一堆文字」，兩件事只有一種解法：要查的那天它在 |
| **純 X／純 Y 只顯示那一軸** | **推翻第一版**（那時寫 `not used`）。按下 X only 的人是自己按的，他知道 Y 還在 —— 那一列對他只是噪音 |
| **Copy** | `X 60 px (150 nm)  Y 44 px (110 nm)`，只帶在用的軸。不然每次都要自己重打 |
| **疊圖點一下放大** | 150 px 對細 pattern 不夠判斷糊不糊，而那是它存在的唯一理由 |
| **Ignore defects（median）** | `stack_cells(method="median")`。大圖中間常常就是缺陷本體，而 mean 會把它抹進 GC |
| **進度講到第幾格** | `build_golden_cell` 本來就回報 `(stage, done, total)`，接起來。7680² 十幾秒，一條跑不完的進度條答不出「它還在動嗎」|

### 15.3 core 那一邊：三票的數字留下來了

（**全部選填、全部有預設值**）。它們本來就算出來了，只是仲裁完就被丟掉。

⚠ 這個 dataclass **不進 recipe、不進 feature、不進黃金值**，所以加欄位不會動到

### 18.1 ⚠ 那個「放大」三輪都沒有生效 —— 這是這一輪最重要的一件事

第 5 點使用者已經講了三輪（§13 的第 1 點、§17.2 的第 4 點、這一輪）。而**每
一輪我都改了、每一輪都沒有生效**：

```python
f = w.font(); f.setPointSizeF(f.pointSizeF() * 2.6); w.setFont(f)
```

兩個獨立的錯：

1. **這個 app 的 QSS 用像素設字級**（`theme` 的 `* { font-size: 13px }`），
   所以 `pointSizeF()` 回 **-1**，乘出來是負數，而 **Qt 對負數的字級是安靜
   忽略的**。
2. 就算改成 `setPixelSize` 也一樣沒用：**QSS 一旦設了 `font-size`，它就贏過
   per-widget 的 `setFont()`**。那條 `*` 規則蓋到每一個 widget。

量出來的真相：`lab_big.font().pixelSize()` = **13**，跟旁邊的說明一模一樣。
1.7× → 1.9× → 2.6× 三輪，畫面上一個像素都沒有變。

> **一個沒有生效的視覺改動，看起來跟沒有被聽見一模一樣。**
> 使用者連著三輪說同一句話，不是他挑剔 —— 是那件事真的沒有發生。

**正確的做法是走 QSS 的 objectName**：`theme` 新增一個 `font_answer` token
（32px）與三條規則（`pitchAnswer` / `pitchAnswerSub` / `pitchAnswerUnit`），
widget 只 `setObjectName`。字級因此跟其他十九個地方住在同一個家（U12 定的
規矩），而不是散在 `setStyleSheet` 裡。

守門：`test_the_answer_is_actually_bigger_than_ordinary_text` —— 它量的是
**渲染出來的 `fontMetrics().height()`**，不是「我們設了什麼」。改回
`setFont()` 的那一天它會紅。（⚠ 測試裡要先 `ensurePolished()`：QSS 是 polish
的時候才套上去的，不 polish 的話三個 widget 都是 Qt 預設字、永遠是綠的。）

### 18.2 第 3 點：打進去的週期也有分數了

`period.confidence_at(image, lag, axis)` —— **不是新演算法**，是
`_analyze_axis` 的尾巴（投影 → 高通 → 去均值 → 正規化自相關 → 在那個 lag 取值）
在一個**呼叫者指定的** lag 上求值。共用同一組私有 helper 是重點：抄第二份出來
的那一份會漂，兩個數字就不能比了。

實測（900×700、px=60 的合成圖）：

| 打進去的 X | 分數 | 意思 |
|---|---|---|
| 60（量到的）| **92.4** | 跟引擎報的 `conf_x` **逐位相同** |
| 59 / 61 | 86.6 / 86.8 | 差 1 px 就看得出來 |
| 61.5 | 83.9 | 次像素在兩個整數 lag 之間內插 |
| **45** | **0.0** | 剛好錯開 —— **長條當場變紅** |
| 120 | 85.8 | 兩倍週期**真的**每 120 px 重複一次，給它誠實的高分 |

⚠ 原本那一格寫 `yours`（§中 `CONF_TYPED`），理由是「不准沿用量出來的分數」。
那個理由**沒有被推翻**，只是它推不出「所以沒有分數」—— 同一個問題可以**對他
打的那個數字重問一次**。`CONF_TYPED` 現在只剩「這張圖打不出分數」的退路。

⚠ 連帶修掉 `Bar` 的一個洞：`if self._frac > 0` 讓 **0 分畫成一條空軌道**，
跟 `set_text_only`（「沒有被評分過」）長得一模一樣。而 0 分正是這個功能最需要
講清楚的那一格。現在 0 分畫一顆紅點。

### 18.3 第 5 點的後半：「copy 是 copy 誰？」

**一顆按鈕的意思是它旁邊那個東西，不是它自己的字。** 它本來住在下面的
`Units` 那一段，離那個答案隔了三個區塊。搬到答案正下方，tooltip 裡放**那一行
字本人**（`Copy "X 60 px (0.150 µm)  Y 44 px (0.110 µm)"`）。

### 18.4 第 2 點：`X + Y` → `Force both`

差別是真的存在的（Auto 會把信心 < 40 的那一軸丟掉，這一顆不會），但 `X + Y`
這個字**只講了它做什麼，沒講它跟 Auto 差在哪**。`Force` 就是那個差別，而那一
句 help 現在以「That is the only difference from Auto」結尾。

> **一個看不出跟隔壁差在哪的選項，是一個陷阱，不是一個選擇。**

### 18.5 第 7 點：打字的中途不算

`setKeyboardTracking(False)` 掛在 `spin_px` / `spin_py` / `spin_nm`。預設 Qt
每敲一個鍵就發 `valueChanged`，於是要打 45 的人會先看到整個視窗用 4 重算一次
—— 一次疊格子是幾百毫秒，而且畫面會**閃一個錯的答案**，而這個視窗的全部內容
就是那一個答案。

### 18.6 第 4 點：字少一點

疊圖那一行本來是三句：「144 cells. Edge cells left out. The cells landed on
each other — this period is right.」而那個結論旁邊就是一條綠色長條寫著 0.98
—— 字只是在重複顏色已經講完的事。現在一句：`144 cells, edges left out —
landed on each other.` 長的那一段留在 tooltip（tooltip 是免費的）。
四顆軸向膠囊的 help 也同樣收短。

### 18.7 順手修掉的一個會閃的 bug

`_fill_try` 換掉候選鈕的時候只做 `removeWidget` ＋ `deleteLater`。
`removeWidget` **不會讓它從畫面上消失** —— 它只是不再由 layout 擺位，於是留在
父視窗上最後一次被擺的地方，而 `deleteLater` 要等事件迴圈。實拍到的樣子是一顆
舊的「60 × 22」候選鈕**疊在最大的那個答案上**。修法是 `setParent(None)`。

### 18.8 ⚠ 順手更正一個我自己講錯的數字

上一輪我說「`main` 的 pyright 是 128、剛好在上限」。**那是錯的：`main` 是
131**（在同一個容器、同一版 pyright、用 `git worktree` 開 `origin/main` 量的），
也就是 `main` 自己就超過它自己的上限 3 條。F120 這條分支**一條都沒有加**
（兩份清單逐行相同）。這一輪把那 3 條修掉了（`numbers.format_feature_value`
的兩路各自收口、`output.py` 的 `source_label` 拿出來再 `callable` 一次），
現在是 **128 = 上限**。

## 19. 第八輪：截其他狀態的圖，截出三個 bug（2026-09-21）

使用者：「好 其他狀態的」。把七個狀態一個一個跑出來截圖 —— **而三個 bug 是
被那幾張圖抓出來的，不是被測試**。這一輪因此又是 §16.3 那一條的證據：
**把它畫出來，那些「跑得完、有數字、而且是錯的」才會現形。**

### 19.1 ⚠ 純 X 模式整個壞掉（而預設值就踩得到）

截 `X only` 那一張看到的是：**格線不見了、`0 cells`、一條紅的
`Cells agree 0.00`、一句「this period is wrong」** —— 而那個 60 px 是對的
（信心 92，而且它本來就是我合成那張圖用的週期）。

病根在 `trim_to_inner` 的第一行：

```python
ox, oy = float(origin[0] or 0.0), float(origin[1] or 0.0)   # ← 錯
```

`lattice_boxes` 裡同一件事寫的是 `oy = float(origin[1]) if periodic[1] else 0.0`
—— **沒在用的那一軸，原點是 0**。`trim_to_inner` 沒有那一句，於是 X only 時
它拿相位搜尋在「一格就是整張高」的 Y 軸上回的那個 `oy`（實測 129）當上邊界，
而格子是從 y=0 開始、700 高 —— **一格都塞不進去**，全部被濾掉。

> **這是這一輪第四次踩到同一種形狀**（`_on_axis`、`_draw` 的週期、畫的格子
> 跟疊的格子、這裡）：**同一件事在畫面上有兩個算法**。四次的修法都一樣：
> 讓第二個算法消失，不是讓它跟第一個對齊。

### 19.2 剪完什麼都不剩的時候，回到沒剪的那一份

`trim_to_inner` 擋的是「沿著哪一軸剪幾格」，它答不出「剪完那一塊裝不裝得下
一個 cell」。而 0 格疊出來的 `agreement` 是 0.00，畫面上長得**跟「這個週期
是錯的」一模一樣**。`_without_edges` 現在先數，少於 `MIN_CELLS_AFTER_TRIM`
就回沒剪的那一份。

> **一個算不出來的答案不准假裝成一個否定的答案。**（同卡片那條「算不出來的
> 那一格不寫」，CLAUDE.md §3。）

### 19.3 ⚠ 被停掉的那一份跑出去了（鐵則 11 在這個視窗的版本）

截「打了一個自己的週期」那一張時，畫面上是 `Cells agree` 空白 ＋ `0 cells`，
而 `_on_done` 收到的明明是一份 20 格的 GoldenCell。追下去是背景 worker：

`run()` 只在**量完週期、還沒開始疊**那一刻檢查 `_stop`。疊圖吃的
`progress=self._tick` 回的是 `not self._stop`，所以停在疊圖中途時
`build_golden_cell` 回一份**只疊了一半、`n_cells` 是 0** 的 GoldenCell，
而下面那一行照樣 `self.done.emit(m, gc, "")` 把它送上畫面。

4096² 疊十幾秒，中途改一個設定就踩得到，而使用者看到的是「這個週期不成立」。
現在疊完再檢查一次 `_stop`，被停掉的那一份發 `(None, None, "")` ——
`_on_done` 對 `m is None` 直接忽略，畫面停在上一個**完整**的答案上。

### 19.4 兩個小的（都是 §18 那兩個改動的反面）

* **還沒疊過的時候不畫那條軌道。** `Bar` 改成「0 分畫一顆點」之後，
  `_fill_stack` 的空狀態（`set_value(0.0, …)`）就變成那個改動的反面：
  「沒有東西可疊」跟「疊了，而它們完全對不起來」畫成同一個樣子。改成
  `set_text_only("")`。
* **沒有答案的時候 Copy 是灰的。** 一顆按下去只會說「還沒量到東西」的按鈕，
  在畫面上是一個問題，不是一個功能。
