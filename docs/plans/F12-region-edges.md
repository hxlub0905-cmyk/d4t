# F12 — 區域也要有線（畫布上那條看不見的依賴）

**狀態**：✅ 完成（2026-08-19）
**起點**：使用者在讀 GDS → GLV 的接法時說「但這樣子是否會違反一開始訂的畫布
DAG 原則，線沒連上不就代表資料流沒往下走?」，接著在我解釋完「跑起來是對的」
之後說「**但我還是這樣怪怪的**」。

那個「怪」是對的，而且它指的不是一個 bug。

---

## 1. 問題：畫布上有兩套規則

```
Load one image ─── single ─────────────────┐   ← 影像：拉線
                                           ▼
Load layout labels ─ layout_label ─▶ GDS layers      Gray-level stats
                                     產生區域 "epi"   roi = "epi"（用打的）
                                          ╎               ▲
                                          └╌╌╌╌ 沒有線 ╌╌╌╌┘
```

影像走**線**，區域走**打字**。使用者要記兩套，而畫面上看不出哪個東西走哪一套。

**它沒有違反鐵則 10 的字面**（那一條管的是影像流的身分要從「全域名字」變成
`(節點, 埠)`，而區域名本來就全域唯一 —— `Context.set_roi` 明文同名覆寫），
執行順序也不靠那條線（`execution_order` 的邊 = **route 相鄰對** ∪ 顯式 edges，
所以 Region 卡一定在量測卡之前跑）。

**但它違反鐵則 10 底下那句真正的不變量：畫布不能說謊。** 現在拿掉 GDS layers
那張卡，量測卡不會報錯 —— 它會**安靜地改量整張圖**，而畫面上兩張卡看起來本來
就互不相干。

痕跡已經在程式碼裡了：三張消費區域的卡，三種 UI。

| 卡 | 區域欄位 | 型別 | 何時做的 |
|---|---|---|---|
| `roi_compare` | target / reference | `region_key`（下拉）| 2026-08-18 |
| `roi_mask` | regions | `region_keys`（勾選）| F11 Region |
| `glv_stats` / `roi_snr` / `cd` | roi | **`str`（自由文字）** | M1 / M2 |

新做的兩張都已經把「區域名」做成打不出錯的欄位。這一輪把它做完，並且**把入口
收成一個**：跟 F9-6 對影像來源做的事完全一樣（使用者當時的話是「他會很亂連」，
於是來源欄位變唯讀、只能拉線）。

## 2. 不變量

> **一張卡用到的每一個具名區域，畫布上都要有一條線指到定義它的那張卡。**

推論三條：

1. 消費區域的參數一律是 `region_key` / `region_keys`，而且 `direction="in"`
   —— 它們在畫布上是**埠**。
2. 設定區那一格**唯讀**（只顯示現在接的是什麼）。改要回畫布上拉線。
3. 剪掉線 = 那一格空掉。跟影像那條路一字不差。

## 3. 關鍵決定：區域線**不存進 recipe**，是推導出來的

`roi="epi"` 這個參數就是唯一的儲存；線是它的**呈現**。拉線 = 設那個參數，
剪線 = 清那個參數。

為什麼不像影像那樣存一條 `Edge`：

* **來源推得出來而且唯一。** 區域名在 `ctx.rois` 裡全域唯一（同名覆寫），
  所以「誰定義了 epi」＝「上游最後一張 `resolve_regions_out` 含 epi 的卡」，
  跟引擎的語意逐字相同。影像流沒有這個性質（同一條 `ref` 可以分岔成兩支），
  那才是 F9 要把身分換成 `(節點, 埠)` 的原因。
* **存了就有兩個家。** 參數與邊各存一份「用哪個區域」，兩者會漂 —— 而 F9 記過
  的六個「跑得完、有數字、而且是錯的」有一半就是這個形狀。
* **舊 recipe 打開就有線**，不必遷移，`to_json_dict → from_json_dict` 仍然是
  identity（鐵則 9）。

代價：區域線不進 `recipe.edges`，所以它不影響 `execution_order` ——
**但那本來就不需要**：route 相鄰對已經保證了順序。畫布的**排版**會吃它
（`layout_columns` 收的是畫出來的線），所以線畫出來仍然是順的。

## 4. 畫法

* 影像線：實線。區域線：**虛線**，顏色用 Region 段的群組色。
* 區域埠：菱形（影像埠是圓）。一眼看得出這兩種線接不到彼此。
* 型別不合的拖放**擋下來並講一句話**（把影像拉進區域埠 = 那格會變成一個
  不存在的區域名，跑起來是 `unknown-region`）。
* 來源排在下游的區域**也擋**：那個名字在這張卡跑到的時候還不存在。

## 6. 做完之後補的兩件事

**① `_autofill_regions` 刪掉了。** F8-UI 當時的做法是「加一張 `roi_mask`，
把上游每一個區域名都填進 `regions`」——區域變成線之後，那等於**自動幫他畫了
好幾條他沒有拉過的線**，正是鐵則 10 擋的那件事（「加卡不准順手接線」）。
它原本的理由（「名字不該要他重打一次」）已經由拉線滿足：埠就在上游那張卡的
右邊。`_autofill_gds_layers` 留著——那是一張**對照表**（層號 → 名字），不是接線。

**② 卡片會長高。** 埠均分卡高，而一張吐三層的 GDS 卡右邊是「一條原樣送出的
流 + 三個區域」。固定 56px 的話它們會擠到重疊，而**重疊的埠點不到**
（`out_port_at` 取最近的那一顆，兩顆疊在一起等於其中一顆消失）。
長高而不是截斷：截掉的區域仍然是這張卡真的產出的東西，看不到就是說謊。

## 7. 第二輪（同日，使用者驗收後）

**① 同進同出。** 使用者：「區域線應該也要 follow 圖像線一樣，前進後出（經過
card 前後一樣的輸入與輸出埠）」。對 —— 接進來的區域，卡片後面也接得出去
（`RecipeModel.region_outputs()` = 自己定義的 ＋ 原樣送出的）。不然兩張卡要量
同一個區域時，第二張只能回頭去接那張 Region 卡，而那條線會橫跨整張畫布。

**這是畫布的事，不是引擎的事**：`ctx.rois` 本來就是全域的。`resolve_regions_out`
一個字都沒有變，而**副標仍然只印「真的產出什麼」**（`regions_produced`）——
兩者混在一起的話，一張 Gray-level stats 在畫布上會讀起來像 Region 卡。
（影像那邊早就是這個形狀：`writes`（埠，含原樣送出）vs `produces`（副標）。）

**② 一個區域埠一條線。** 使用者：「區域線一次只能連一條，重新拉會取代原來的」。
成立，而且是**結構性**的：`region_key` 那一格只放得下一個名字，所以「留下兩條」
表達不出來 —— 而線是從那一格推導出來的，舊線在同一個動作裡就消失了。
（`region_keys`（`roi_mask` 的 `regions`）是清單，第二條線是「這個也算」——
跟 `image_keys` 同一條規則。）測試把兩者都鎖起來了。
