# F8 — 純規則的 ROI 定位（兩組條紋的交會處）

**狀態：核心完成（2026-08-13）。**

---

## 1. 需求從哪裡來

使用者試用 `Locate region by profile` 之後說：

> 「我沒辦法做 ROI 定位。我目前有幾招：第一是載入 GDS（連動 GLAS 專案，但需求是
> 要有 oas 檔案），第二個是 Locate region by template（載入 GC 模板）。
> **但我還是希望有一種是不需要外部、單純靠純 rule 就能將 ROI 區域的 BOX 訂出來**
> 這樣。我本來預期投影要可以的，但我不知道怎麼跟你描述比較適合。」

追問之後，要框的東西是：

> 「例如 patch 內我有 MG（Metal Gate）跟 EPI 位置，**MG 是直的 EPI 是橫的**，
> 我想要框的位置可能是 MG 跟 EPI 交界處（**在 EPI 上**）…
> 可能會有好幾個交界，因為一張 patch 會有好幾根 MG 跟好幾根 EPI，
> 所以 **ROI 會是分散的 BOX**。」

加上一個關鍵條件：**MG 的 pitch 是 GDS 定義的，一定準。**

## 2. 為什麼原本做不到

`roi_profile` 差的不是演算法，是最後一步。它產生區域的那一行：

```python
def _band_rect(band, length, axis):
    """另一個方向取滿：投影只知道「沿著這條軸的哪一段」，
    對另一個方向一無所知，硬給一個高度等於憑空捏造資訊。"""
    if axis == "x":
        return (lo, 0.0, span, 1.0)   # 一條「滿高」的垂直條紋
    return (0.0, lo, 1.0, span)       # 一條「滿寬」的水平條紋
```

那個拒絕對**一次**投影是對的。它擋掉的是另一件事：**另一個方向的範圍不需要
猜，再投影一次就量得到。** 而且 `rule` 只挑**一段**，所以連「好幾個框」都表達
不出來。

現況全貌（F8 之前）：

| 招 | 卡片 | 要外部檔案 | 產出 |
|---|---|---|---|
| GDS | GLAS 連動 | **要 .oas** | 方框 |
| GC 模板 | `roi_template` | **要一張原大圖** | 方框 |
| 固定框 | `roi_define` | 不用 | 方框，但位置固定在畫面上 |
| 缺陷分割 | `blob_segment` | 不用 | 框住**缺陷本身**，不是圖案 |
| 投影 | `roi_profile` | 不用 | **只有條紋** |

「不靠外部檔案、純規則、框出圖案上的 BOX」那一格是空的。而 `region.py` 的模組
說明其實早就寫明這件事該長什麼樣（pattern frame，標為「尚未實作」）。

## 3. 為什麼**不**走週期估測

`region.py` 指名的路是 `algo/period.py` 的 `estimate_period` / `choose_origin`。
這一輪**刻意不走**，三個理由：

1. **patch 太小。** 使用者的 patch 是 64–128 px。`estimate_period` 的信心門檻是
   40（純雜訊實測 20.3），需要 2–3 個完整週期才可靠 —— pitch 20–30 px 時只有
   2–4 個週期，正是它最不可靠的區間。
2. **根本不需要估。** 投影是**直接量到**每一根線在哪，不是從週期外推的。
   少一層假設就少一種失敗方式；pitch 不均、邊緣缺一根都不影響。
3. **會跟 `roi_template` 重疊**（使用者自己指出來的）。Golden Cell 的本質就是
   「拿一個完整 cell 對回相位」，跟週期＋相位是同一件事的兩種做法。

`period.py` 仍然不刪（CLAUDE.md §11 的警告照舊）—— 只是這件事不歸它做。

## 4. 做了什麼

### `adept/core/algo/grid.py`

```
X 投影 → 一組直的條紋 ─┐
                        ├→ 交叉成格 → 挑格 → 微調 → N 個 BOX
Y 投影 → 一組橫的條紋 ─┘
```

只認得「**這個方向有一組條紋**」。誰是 MG、誰是 EPI、誰亮誰暗，程式不需要知道
—— 使用者回答的是三個對任何 layout 都成立的問題：哪個方向、要暗的還是亮的
（**相對**亮度，不是絕對灰階）、框放在交會處的哪裡。

五種放法：`crossing` / `beside_vertical` / `beside_horizontal` /
`between_vertical` / `between_horizontal`。後面接的是**被貼住的那組條紋**，
另一組永遠是限制框長度的那一邊，所以五個值各自說得完自己是什麼。

### 已知 pitch 做三件事

1. **驗證** —— 量到的間距對不對（`pitch_error`）。
2. **補線** —— 邊緣只露一半、對比不足而漏掉的那幾根補回來（`filled`）。
3. **把錨定條件從「要好幾個週期」降成「要一根條紋」** —— 64 px 上的決定性差別。

**對不上就不用它**（誤差 > `pitch × 0.25`）：pitch 是外面帶進來的假設，影像是
這一顆真的長的樣子。衝突時相信影像，把證據留給上層講出來。

⚠ **pitch 一律是像素。** GDS 給的是 nm，而 `nm_per_px` 在 KLARF 裡沒有來源
（CLAUDE.md §8）—— 收 nm 的話它會變成第二個恆為 0 的 `cd_x_nm`。

### `adept/core/steps/roi_cross.py`

一張卡 `Locate regions where patterns cross`，產出**兩個**區域：

* `<name>` —— 全部的框（多框區域）
* `<name>_center` —— 離 patch 正中心最近的那一塊，也就是**缺陷所在的那一塊**

特徵：`cross_count` / `cross_pitch_x_px` / `cross_pitch_y_px` / `cross_filled` /
`cross_dist_px` / `locate_conf` / `locate_ok`。

### 多框區域（引擎）

`Context.set_roi_boxes()` / `roi_count()` / `roi_rects()` / `roi_norm_rects()`。
一個名字底下可以有好幾個框；單框只是 N=1，既有的卡完全不受影響。

* `glv_stats` 改讀 `_util.roi_pixels()` —— 統計量只需要「有哪些像素」，
  所以分散的 N 個框就是一個像素母體。
* 要幾何的卡（`cd_measure`）遇到多框區域**拋錯並指路**（去用 `_center`），
  不是安靜地拿第一個。
* `region_check` 畫**每一個**框 —— 只畫第一個的話畫面會說謊。

### UI

`CrossInspector`（依 `Step.key` 註冊）：兩個方向各一條曲線 + 選中的條紋 +
一行摘要。交會處是兩組條紋共同定義的，所以失敗也有兩種、處置完全不同 ——
只給一條曲線的話，使用者只知道「失敗了」，卻不知道該調哪一半。

`ProfilePanel` 加上 `selected`（畫**好幾段**，不只一段）。

## 5. 踩到的坑

### 晶格要排在條紋的**中心**上，不是排在邊界上

**這一輪最貴的一個。** 一根寬 8、週期 24 的條紋，它的**邊界**間距是
8、16、8、16… 交錯的，只有**中心**才是每 24 一次。第一版拿邊界去對等距晶格，
把一根條紋的兩條邊併成一格 —— 條紋寬度整個消失、框落到隨機的地方。

而它**看起來完全像對的**：`ok=True`、框的數量合理、位置整齊。是量了每個框的
平均灰階（該是 EPI 的 170）才發現一半的框是 70。

### 框要離邊界一點（`gap`）

轉折是在**平滑過的**曲線上用中央差分找的，位置會早一格左右；而邊界本身在 SEM
上就糊在好幾個像素上。實測：`gap=0` 時 5px 的框吃進一欄另一種材質，
平均 170 → 157.5（最差 144），而 `gap=1` 是 170.0、框跟框之間的標準差
從 12.5 掉到 0.3。

**一成多的偏差，而且仍然是個看起來很正常的數字。**

### 失敗訊息要講出是**哪個方向**

「信心不足」只說得出「失敗了」。這張卡有兩組 sensitivity / pitch，使用者下一步
該做什麼完全取決於是哪一邊沒抓到。

## 6b. 第二輪（試用回饋，同日）

三件事，都是「拿真的 layout 一比就發現」的：

### 框要**即時**疊在預覽影像上

> 「不然都一定按 Check this region across defects… 跑完才能看，不能實時調整」

`ImageView.set_overlay()`（正規化座標，跟著縮放平移走）+ Studio 每次預覽算完就
重畫一次。定位卡的參數是**一邊拖一邊看**決定的（F7-8 那條：「先想好一個數字
再輸入」那個順序是反的）；框只出現在另一個要按鈕、要跑完一批的視窗裡，等於把
調敏感度變成「改一次、跑一次、再回來看」，而那要試十幾次。

只畫**選著那張卡**自己宣告的區域 —— 一份 recipe 常有好幾張 Region 卡，全部畫
出來會變成一團分不清誰是誰的線。離 patch 正中心最近的那個框畫成醒目色
（缺陷永遠在那裡），其餘畫細線：一堆一模一樣的框裡看不出哪個是「這一顆」的。

### 三層以上的灰階（`dark`/`bright` 不夠用）

> 「for MG 跟 EPI，MG 是最亮的（GLV 約 220），EPI 次之（約 180）」

原本的中位數二分法會把 220 跟 180 併成「亮的那一組」，於是「我要第二亮的那組」
講不出來。改成**排名**：`brightest` / `second_brightest` / `third_brightest`
及暗端的三個。分成幾群由排名決定（要第二亮就分三群），使用者只要回答一個問題
—— 不必再猜「這張圖有幾種材質」，那是**另一個**問題，多問一次就多一次填錯的
機會。

分群切在**排序後最大的間隙**上（一維自然斷點）：材質之間的灰階差本來就是一個個
台階，而台階之間的間隙遠大於同一種材質內部的起伏。不用 k-means —— 不需要迭代、
不需要種子，同一張圖每次跑的答案完全相同（批次快取的前提）。

⚠ 值得講清楚的一點：**每個方向各自判斷**。MG 是直的、EPI 是橫的，所以在
X 投影裡 MG 是最亮的欄，在 Y 投影裡 EPI 是最亮的列 —— 兩邊都填 `brightest`。
排名是給「**同一個方向**有三層以上」的情況用的。

舊值 `dark` / `bright` 由 `recipe._migrate_renamed_values` 換名。**相容性是檔案
格式的事，不是把兩個意思一樣的選項留在下拉選單裡。**

### 交錯的 pitch

> 「EPI 跟 EPI 之間的 pitch 有兩種」

`vertical_pitch_2` / `horizontal_pitch_2`（0 = 不交錯）。晶格從錨點往兩邊走，
間距依序取那兩個值。錨點落在交錯的哪一相是看不出來的，所以**每一相都排一次，
留誤差最小的那個**。兩種間距時「pitch 是多少」沒有單一答案 —— 特徵報平均，
完整的一組留在 `pitches_used`。

超過兩種間距沒有做（要的是一個清單型參數，而那會讓這一格從滑桿變成自由文字）。

## 6c. 第三輪（試用回饋）

### 「Box 目前好像左右會歪歪的」—— 真的歪，而且量得出來

**這一輪最重要的一條。** 使用者猜是「致中的 box 在搞鬼」，不是 —— `_center`
只是在既有的框裡**挑**一個，它不會移動任何框。真正的原因在邊界偵測：

`|梯度|` 的峰**通常是一個 2 格寬的平台**（實測 `grad[20] == grad[21]`，位元
完全相同），而 `find_transitions` 挑局部極大的條件左右不對稱（`> 左鄰` 但
`>= 右鄰`），於是同一根條紋的兩條邊各挑到平台的不同側。實測：

```
detected [ 23, 32)  真值 [ 24, 32)  → 左偏 -1  右偏 +0     ← 每一根都一樣
```

段往左胖了一格 → 貼在兩側的框**一邊有縫、一邊沒縫**。而兩個框量的是同一種
材質，所以**數字上完全看不出來**，只有畫面上看得出來。

修法是 `refine_edges()`：拋物線內插把峰放回 20.5（真實邊界就在 20 與 21 之間），
段的幾何改用次像素位置。順帶抓到兩個附帶的坑：

* **Python 的 `round()` 是 banker's rounding**（`round(14.5)==14` 但
  `round(15.5)==16`）。次像素邊界精修之後每一條邊都正好落在 `.5` 上 ——
  同一個框的兩端會用不同規則進位，框寬時而 5 時而 6。改用 `floor(v+0.5)`。
* **而 `.5` 算出來其實是 `20.499997`**（浮點）。差在最後幾個 bit，卻決定捨上
  還是捨下，**而一根條紋的左右兩條邊剛好落在不同邊** —— 修完 banker's rounding
  之後仍然左 2 格右 1 格。加 `1e-6` 的容差把「數學上是 .5」還原成 .5。
* 切到影像邊緣而窄掉的框**丟掉**（以前留一個六成寬的）。那幾個框的意義是
  「同一種東西的同一種取樣」，殘框在統計上是稀釋、在畫面上是那一排裡突然有
  一個比較短。

驗收：`test_the_two_boxes_beside_a_stripe_are_the_same_distance_from_it`
（左右縫差 < 0.01 px）、`test_the_stripe_width_survives_the_edge_detection`、
`test_every_box_has_the_width_that_was_asked_for`。三條都在**糊掉的邊界**上跑
—— 銳利的階梯剛好沒有平台，這個 bug 只在真實的（糊的）邊界上出現。

### 「這張卡的 UI 有點亂，有些我不知道是什麼功能」

19 個參數攤成一排，每一列看起來都同等重要、同等神秘 —— 而它們其實在回答**五個
不同的問題**。新增 `ParamSpec.section`：同一組畫在一起、上面一行小標題，
順序就是操作順序（1 哪張圖 → 2 直的條紋 → 3 橫的條紋 → 4 框放哪 → 5 名字）。

`show_when` 解的是「這一列現在算不算數」，`section` 解的是「這一列在回答哪個
問題」—— 兩者不能互相取代。整組被 `show_when` 藏光時標題跟著收起來：一個底下
什麼都沒有的標題，比沒有標題更讓人以為畫面壞了。

順帶把 `smooth` 從「橫的條紋」那組搬到第一組並改名成
`Curve smoothing (both directions)` —— 它兩個方向共用，掛在其中一組底下會讓人
以為只影響那一邊。

這是 `ParamSpec` 層的通用機制，`normalize`（10 個參數）之後也用得上。

### 「Crossing 的那條灰色虛線，我可以操作嗎？」

不行，它是**參考線**：patch 正中心，也就是機台裁切時放缺陷的地方。
一條沒有說明的虛線看起來就像可以拖的東西，所以現在線旁邊標了 `defect`，
面板的 tooltip 也講明「it is a marker, not something you set」。

（順帶回答使用者的顧慮：缺陷確實只是**接近**正中心而不是剛好。這對
`<name>_center` 沒有影響 —— 它挑的是「最近的那一個框」，而框與框之間隔著一個
pitch，差一兩個像素不會換人。）

## 7. 沒做的

* **`roi_profile` 沒有被取代。** 只要一段條帶的場合它仍然更簡單。
* **框只有正矩形。** 旋轉的 layout 要先轉正（沒有卡片做這件事）。
* **兩組以上的條紋**（例如三種材質交錯）沒有處理。
* **`max_boxes` 砍掉的是最外圍的**，而且只在 `reason` 裡講一句。
  框很多的時候使用者不一定會看到。
* **pitch 仍然要人填。** 站點知道 nm，這裡要 px —— 兩者之間的換算沒有自動化，
  因為 `nm_per_px` 在 KLARF 裡沒有來源（§8）。
