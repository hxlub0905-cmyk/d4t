# F8 — 純規則的 ROI 定位（兩組條紋的交會處）

**狀態：核心完成（2026-08-13）。**

---

## 1. 需求從哪裡來

使用者試用 `Locate region by profile` 之後說：

> 「我沒辦法做 ROI 定位。我目前有幾招：第一是載入 GDS（連動 GLAS 專案，但需求是
> 要有 oas 檔案），第二個是 Locate region by template（載入 GC 模板）。
> **但我還是希望有一種是不需要外部、單純靠純 rule 就能將 ROI 區域的 BOX 訂出來**
> 這樣。我本來預期投影要可以的，但我不知道怎麼跟你描述比較適合。」

追問之後，要框的東西是：

> 「例如 patch 內我有 MG（Metal Gate）跟 EPI 位置，**MG 是直的 EPI 是橫的**，
> 我想要框的位置可能是 MG 跟 EPI 交界處（**在 EPI 上**）…
> 可能會有好幾個交界，因為一張 patch 會有好幾根 MG 跟好幾根 EPI，
> 所以 **ROI 會是分散的 BOX**。」

加上一個關鍵條件：**MG 的 pitch 是 GDS 定義的，一定準。**

## 2. 為什麼原本做不到

`roi_profile` 差的不是演算法，是最後一步。它產生區域的那一行：

```python
def _band_rect(band, length, axis):
    """另一個方向取滿：投影只知道「沿著這條軸的哪一段」，
    對另一個方向一無所知，硬給一個高度等於憑空捏造資訊。"""
    if axis == "x":
        return (lo, 0.0, span, 1.0)   # 一條「滿高」的垂直條紋
    return (0.0, lo, 1.0, span)       # 一條「滿寬」的水平條紋
```

那個拒絕對**一次**投影是對的。它擋掉的是另一件事：**另一個方向的範圍不需要
猜，再投影一次就量得到。** 而且 `rule` 只挑**一段**，所以連「好幾個框」都表達
不出來。

現況全貌（F8 之前）：

| 招 | 卡片 | 要外部檔案 | 產出 |
|---|---|---|---|
| GDS | GLAS 連動 | **要 .oas** | 方框 |
| GC 模板 | `roi_template` | **要一張原大圖** | 方框 |
| 固定框 | `roi_define` | 不用 | 方框，但位置固定在畫面上 |
| 缺陷分割 | `blob_segment` | 不用 | 框住**缺陷本身**，不是圖案 |
| 投影 | `roi_profile` | 不用 | **只有條紋** |

「不靠外部檔案、純規則、框出圖案上的 BOX」那一格是空的。而 `region.py` 的模組
說明其實早就寫明這件事該長什麼樣（pattern frame，標為「尚未實作」）。

## 3. 為什麼**不**走週期估測

`region.py` 指名的路是 `algo/period.py` 的 `estimate_period` / `choose_origin`。
這一輪**刻意不走**，三個理由：

1. **patch 太小。** 使用者的 patch 是 64–128 px。`estimate_period` 的信心門檻是
   40（純雜訊實測 20.3），需要 2–3 個完整週期才可靠 —— pitch 20–30 px 時只有
   2–4 個週期，正是它最不可靠的區間。
2. **根本不需要估。** 投影是**直接量到**每一根線在哪，不是從週期外推的。
   少一層假設就少一種失敗方式；pitch 不均、邊緣缺一根都不影響。
3. **會跟 `roi_template` 重疊**（使用者自己指出來的）。Golden Cell 的本質就是
   「拿一個完整 cell 對回相位」，跟週期＋相位是同一件事的兩種做法。

`period.py` 仍然不刪（CLAUDE.md §11 的警告照舊）—— 只是這件事不歸它做。

## 4. 做了什麼

### `adept/core/algo/grid.py`

```
X 投影 → 一組直的條紋 ─┐
                        ├→ 交叉成格 → 挑格 → 微調 → N 個 BOX
Y 投影 → 一組橫的條紋 ─┘
```

只認得「**這個方向有一組條紋**」。誰是 MG、誰是 EPI、誰亮誰暗，程式不需要知道
—— 使用者回答的是三個對任何 layout 都成立的問題：哪個方向、要暗的還是亮的
（**相對**亮度，不是絕對灰階）、框放在交會處的哪裡。

五種放法：`crossing` / `beside_vertical` / `beside_horizontal` /
`between_vertical` / `between_horizontal`。後面接的是**被貼住的那組條紋**，
另一組永遠是限制框長度的那一邊，所以五個值各自說得完自己是什麼。

### 已知 pitch 做三件事

1. **驗證** —— 量到的間距對不對（`pitch_error`）。
2. **補線** —— 邊緣只露一半、對比不足而漏掉的那幾根補回來（`filled`）。
3. **把錨定條件從「要好幾個週期」降成「要一根條紋」** —— 64 px 上的決定性差別。

**對不上就不用它**（誤差 > `pitch × 0.25`）：pitch 是外面帶進來的假設，影像是
這一顆真的長的樣子。衝突時相信影像，把證據留給上層講出來。

⚠ **pitch 一律是像素。** GDS 給的是 nm，而 `nm_per_px` 在 KLARF 裡沒有來源
（CLAUDE.md §8）—— 收 nm 的話它會變成第二個恆為 0 的 `cd_x_nm`。

### `adept/core/steps/roi_cross.py`

一張卡 `Locate regions where patterns cross`，產出**兩個**區域：

* `<name>` —— 全部的框（多框區域）
* `<name>_center` —— 離 patch 正中心最近的那一塊，也就是**缺陷所在的那一塊**

特徵：`cross_count` / `cross_pitch_x_px` / `cross_pitch_y_px` / `cross_filled` /
`cross_dist_px` / `locate_conf` / `locate_ok`。

### 多框區域（引擎）

`Context.set_roi_boxes()` / `roi_count()` / `roi_rects()` / `roi_norm_rects()`。
一個名字底下可以有好幾個框；單框只是 N=1，既有的卡完全不受影響。

* `glv_stats` 改讀 `_util.roi_pixels()` —— 統計量只需要「有哪些像素」，
  所以分散的 N 個框就是一個像素母體。
* 要幾何的卡（`cd_measure`）遇到多框區域**拋錯並指路**（去用 `_center`），
  不是安靜地拿第一個。
* `region_check` 畫**每一個**框 —— 只畫第一個的話畫面會說謊。

### UI

`CrossInspector`（依 `Step.key` 註冊）：兩個方向各一條曲線 + 選中的條紋 +
一行摘要。交會處是兩組條紋共同定義的，所以失敗也有兩種、處置完全不同 ——
只給一條曲線的話，使用者只知道「失敗了」，卻不知道該調哪一半。

`ProfilePanel` 加上 `selected`（畫**好幾段**，不只一段）。

## 5. 踩到的坑

### 晶格要排在條紋的**中心**上，不是排在邊界上

**這一輪最貴的一個。** 一根寬 8、週期 24 的條紋，它的**邊界**間距是
8、16、8、16… 交錯的，只有**中心**才是每 24 一次。第一版拿邊界去對等距晶格，
把一根條紋的兩條邊併成一格 —— 條紋寬度整個消失、框落到隨機的地方。

而它**看起來完全像對的**：`ok=True`、框的數量合理、位置整齊。是量了每個框的
平均灰階（該是 EPI 的 170）才發現一半的框是 70。

### 框要離邊界一點（`gap`）

轉折是在**平滑過的**曲線上用中央差分找的，位置會早一格左右；而邊界本身在 SEM
上就糊在好幾個像素上。實測：`gap=0` 時 5px 的框吃進一欄另一種材質，
平均 170 → 157.5（最差 144），而 `gap=1` 是 170.0、框跟框之間的標準差
從 12.5 掉到 0.3。

**一成多的偏差，而且仍然是個看起來很正常的數字。**

### 失敗訊息要講出是**哪個方向**

「信心不足」只說得出「失敗了」。這張卡有兩組 sensitivity / pitch，使用者下一步
該做什麼完全取決於是哪一邊沒抓到。

## 6b. 第二輪（試用回饋，同日）

三件事，都是「拿真的 layout 一比就發現」的：

### 框要**即時**疊在預覽影像上

> 「不然都一定按 Check this region across defects… 跑完才能看，不能實時調整」

`ImageView.set_overlay()`（正規化座標，跟著縮放平移走）+ Studio 每次預覽算完就
重畫一次。定位卡的參數是**一邊拖一邊看**決定的（F7-8 那條：「先想好一個數字
再輸入」那個順序是反的）；框只出現在另一個要按鈕、要跑完一批的視窗裡，等於把
調敏感度變成「改一次、跑一次、再回來看」，而那要試十幾次。

只畫**選著那張卡**自己宣告的區域 —— 一份 recipe 常有好幾張 Region 卡，全部畫
出來會變成一團分不清誰是誰的線。離 patch 正中心最近的那個框畫成醒目色
（缺陷永遠在那裡），其餘畫細線：一堆一模一樣的框裡看不出哪個是「這一顆」的。

### 三層以上的灰階（`dark`/`bright` 不夠用）

> 「for MG 跟 EPI，MG 是最亮的（GLV 約 220），EPI 次之（約 180）」

原本的中位數二分法會把 220 跟 180 併成「亮的那一組」，於是「我要第二亮的那組」
講不出來。改成**排名**：`brightest` / `second_brightest` / `third_brightest`
及暗端的三個。分成幾群由排名決定（要第二亮就分三群），使用者只要回答一個問題
—— 不必再猜「這張圖有幾種材質」，那是**另一個**問題，多問一次就多一次填錯的
機會。

分群切在**排序後最大的間隙**上（一維自然斷點）：材質之間的灰階差本來就是一個個
台階，而台階之間的間隙遠大於同一種材質內部的起伏。不用 k-means —— 不需要迭代、
不需要種子，同一張圖每次跑的答案完全相同（批次快取的前提）。

⚠ 值得講清楚的一點：**每個方向各自判斷**。MG 是直的、EPI 是橫的，所以在
X 投影裡 MG 是最亮的欄，在 Y 投影裡 EPI 是最亮的列 —— 兩邊都填 `brightest`。
排名是給「**同一個方向**有三層以上」的情況用的。

舊值 `dark` / `bright` 由 `recipe._migrate_renamed_values` 換名。**相容性是檔案
格式的事，不是把兩個意思一樣的選項留在下拉選單裡。**

### 交錯的 pitch

> 「EPI 跟 EPI 之間的 pitch 有兩種」

`vertical_pitch_2` / `horizontal_pitch_2`（0 = 不交錯）。晶格從錨點往兩邊走，
間距依序取那兩個值。錨點落在交錯的哪一相是看不出來的，所以**每一相都排一次，
留誤差最小的那個**。兩種間距時「pitch 是多少」沒有單一答案 —— 特徵報平均，
完整的一組留在 `pitches_used`。

超過兩種間距沒有做（要的是一個清單型參數，而那會讓這一格從滑桿變成自由文字）。

## 6c. 第三輪（試用回饋）

### 「Box 目前好像左右會歪歪的」—— 真的歪，而且量得出來

**這一輪最重要的一條。** 使用者猜是「致中的 box 在搞鬼」，不是 —— `_center`
只是在既有的框裡**挑**一個，它不會移動任何框。真正的原因在邊界偵測：

`|梯度|` 的峰**通常是一個 2 格寬的平台**（實測 `grad[20] == grad[21]`，位元
完全相同），而 `find_transitions` 挑局部極大的條件左右不對稱（`> 左鄰` 但
`>= 右鄰`），於是同一根條紋的兩條邊各挑到平台的不同側。實測：

```
detected [ 23, 32)  真值 [ 24, 32)  → 左偏 -1  右偏 +0     ← 每一根都一樣
```

段往左胖了一格 → 貼在兩側的框**一邊有縫、一邊沒縫**。而兩個框量的是同一種
材質，所以**數字上完全看不出來**，只有畫面上看得出來。

修法是 `refine_edges()`：拋物線內插把峰放回 20.5（真實邊界就在 20 與 21 之間），
段的幾何改用次像素位置。順帶抓到兩個附帶的坑：

* **Python 的 `round()` 是 banker's rounding**（`round(14.5)==14` 但
  `round(15.5)==16`）。次像素邊界精修之後每一條邊都正好落在 `.5` 上 ——
  同一個框的兩端會用不同規則進位，框寬時而 5 時而 6。改用 `floor(v+0.5)`。
* **而 `.5` 算出來其實是 `20.499997`**（浮點）。差在最後幾個 bit，卻決定捨上
  還是捨下，**而一根條紋的左右兩條邊剛好落在不同邊** —— 修完 banker's rounding
  之後仍然左 2 格右 1 格。加 `1e-6` 的容差把「數學上是 .5」還原成 .5。
* 切到影像邊緣而窄掉的框**丟掉**（以前留一個六成寬的）。那幾個框的意義是
  「同一種東西的同一種取樣」，殘框在統計上是稀釋、在畫面上是那一排裡突然有
  一個比較短。

驗收：`test_the_two_boxes_beside_a_stripe_are_the_same_distance_from_it`
（左右縫差 < 0.01 px）、`test_the_stripe_width_survives_the_edge_detection`、
`test_every_box_has_the_width_that_was_asked_for`。三條都在**糊掉的邊界**上跑
—— 銳利的階梯剛好沒有平台，這個 bug 只在真實的（糊的）邊界上出現。

### 「這張卡的 UI 有點亂，有些我不知道是什麼功能」

19 個參數攤成一排，每一列看起來都同等重要、同等神秘 —— 而它們其實在回答**五個
不同的問題**。新增 `ParamSpec.section`：同一組畫在一起、上面一行小標題，
順序就是操作順序（1 哪張圖 → 2 直的條紋 → 3 橫的條紋 → 4 框放哪 → 5 名字）。

`show_when` 解的是「這一列現在算不算數」，`section` 解的是「這一列在回答哪個
問題」—— 兩者不能互相取代。整組被 `show_when` 藏光時標題跟著收起來：一個底下
什麼都沒有的標題，比沒有標題更讓人以為畫面壞了。

順帶把 `smooth` 從「橫的條紋」那組搬到第一組並改名成
`Curve smoothing (both directions)` —— 它兩個方向共用，掛在其中一組底下會讓人
以為只影響那一邊。

這是 `ParamSpec` 層的通用機制，`normalize`（10 個參數）之後也用得上。

### 「Crossing 的那條灰色虛線，我可以操作嗎？」

不行，它是**參考線**：patch 正中心，也就是機台裁切時放缺陷的地方。
一條沒有說明的虛線看起來就像可以拖的東西，所以現在線旁邊標了 `defect`，
面板的 tooltip 也講明「it is a marker, not something you set」。

（順帶回答使用者的顧慮：缺陷確實只是**接近**正中心而不是剛好。這對
`<name>_center` 沒有影響 —— 它挑的是「最近的那一個框」，而框與框之間隔著一個
pitch，差一兩個像素不會換人。）

## 6d. 第四輪：pitch 除不盡、以及線寬

使用者問了兩個問題，兩個都查出東西。

### 「pixel size 1.5 nm、MG pitch 44 nm，除不盡怎麼表現？」

44 / 1.5 = **29.333… px**。答案是**照著填分數**（欄位是 float、收三位小數），
而**不要自己先四捨五入**。改了兩處讓這件事真的成立：

* **`_fill_by_pitch` 不再把補出來的段捨成整數格。** 晶格是浮點累加的，但舊版
  一算完就 `_clip_span` 捨掉 —— 每一根各自被推掉最多半格，而那半格正是框貼不貼
  得住邊界的差別。捨入留到最後做框時一次做完。
* **相位改用整排一起定**（所有量到的中心對晶格的偏移取中位數），不再只靠錨點
  那一根。錨點自己也是量出來的，它的誤差會原封不動平移整個晶格；每一根的誤差
  彼此獨立，中位數就洗掉了。被影像邊界切到的那幾根**不參加** —— 它們只露一半，
  「中心」依定義就是偏的。

實測（160 px、pitch 29.333、只比沒被切到的那幾根）：

| | 最大偏差 |
|---|---|
| 不填，自己量 | 0.83 px |
| **填 29.333** | **0.50 px**（而且不漂移，逐根都是 0.5）|
| 填 29（自己捨） | 逐根 0.25 / 0.08 / 0.42 / 0.75 / 1.08 —— **越遠越差** |

「越遠越差」才是自己捨去真正危險的地方：patch 中央（缺陷所在）看起來還好好的，
歪掉的是最外圍。驗收 `test_the_lattice_never_quantises_the_pitch_it_was_given`
直接鎖晶格產生器（差多少是算術，不該用一張只放得下四五個週期的合成圖去演）。

### 「MG 自己也有自己的寬，這你有假設進去嗎？」

有，而且是**量的不是假設的** —— 線寬沒有參數。實測 8 / 12 / 18 px 三種線寬都
量到 ±1 px 以內，換線寬不必改 recipe。

**但這一問查出一個真的 bug。** 舊版在填了 pitch 之後，把整排的寬度統一成
**中位數**：

```
真實寬度   [15.27, 7.91, 12.67, 11.09, 11.28, 11.66]
填了 pitch [11.25, 11.5, 11.5, 11.5, 11.5, 11.5]   ← 全被抹平
```

pitch 講的是「每隔多遠有一根」，**它對線寬一個字都沒說**。抹平的後果不只是丟掉
line-width roughness（那有時候正是缺陷本身）：框是貼著段的**邊界**放的，所以在
線寬異常的那一根上，框會被推進 MG 裡面好幾個像素 —— **最需要量準的那一根，
量得最髒**。

改成：每一根用**自己量到的**寬度，只有影像上根本沒有、靠 pitch 補出來的那幾根
才借中位數（它們沒有自己的量測值可用）。驗收
`test_filling_in_the_pitch_does_not_flatten_the_line_widths` 與
`test_only_the_invented_stripes_borrow_the_median_width`。

## 6e. 第五輪：量測尺、CPODE、給定線寬

三件事，來源都是同一次試用。

### 量測尺（「不知道 pitch 的時候，從 profile 量出來」）

`vertical_pitch` / `horizontal_pitch` 可以留白（留白就靠影像自己量），但條紋一髒，
那張卡就會要求使用者填一個**他不知道的數字** —— 而畫面上唯一握有這個資訊的東西
正是那條曲線。

`ProfilePanel` 按住拖曳量測，放開就結束（它是「現在正在量」的回饋，不是留在畫面
上的註記）。三個決定：

* **讀數不只講距離，還算 pitch。** 量一個週期是所有量法裡最不準的一種 —— 兩端
  各差一個像素，pitch 就差兩個。橫跨好幾根再除以根數，誤差被根數除掉。所以只要
  這一段裡有兩根以上抓到的條紋（用**中心**判定，不用邊界 —— 邊界有升有降會多算
  一倍），就順便把 pitch 算給他。
* **綠色是刻意換一個色相的。** 曲線是墨色、轉折線是 accent、選中的段是 accent 的
  淡底。尺再從那一家挑一個色階的話，「哪一條是我剛剛拉的」就只剩深淺可分，
  而深淺會被主題與縮放吃掉（跟 F7-18 的虛線同一條）。
* **上面那張影像同步標同一段**（`ImageView.set_measure`）。曲線上的一段只是
  「第 40 到第 74 個取樣點」，而「我量到的是不是兩根 MG 的距離」只有看影像
  答得出來。並排比對開著時兩張都標。

繪製與命中判定共用 `_plot_rect()`：兩邊各自算一次的話，尺會跟曲線差幾個像素，
那種偏差肉眼看不出來卻會讓讀數一直是錯的。換卡片時把尺收掉 —— 面板被拆掉就
不會再有「放開」，綠帶會永遠留在影像上。

驗收 `tests/test_ui_f8_ruler.py`（17 條）。

### CPODE：同一個晶格上第三種材質

使用者原話：「如果某側出現 CPODE（可以把他想成很暗的 MG，寬度跟 MG 一樣，
也就是把 MG 挖掉，pitch 是跟 MG 共用的），可能一張 patch 由左到右是
MG-MG-CPODE，這樣要怎麼設定？」

先照舊版跑一次（128 px、MG pitch 24、寬 8，第 2 與第 5 格換成 CPODE）：

| | 抓到幾根 | 量到的 pitch | `pitch_error` |
|---|---|---|---|
| `select=brightest`（舊） | **9** | **12.0**（一半） | — |
| 再填 `pitch=24` | 5 | 24.0 | **0.00** |

第一列是「最亮的那一群」把**空隙**也收進來了：三個台階（MG 216／空隙 133／
CPODE 41）分兩群時，最大的間隙落在 CPODE 與空隙之間。第二列更糟 —— 晶格照樣排出
一組間距完全正確的解，只是它鎖在**空隙**上而不是 MG 上，而 `pitch_error` 是 0.00，
看起來完美。**這是安靜的錯答案**，畫面上不會有任何一個字說出這件事。

所以 `select_bands` 多一個 `kinds`：**這個方向上有幾種條紋**（不是「分幾群」——
使用者答得出前者）。0 = 照排名推（舊行為），同一個晶格上多一種材質就加一。
排名要求的群數是**下限**（「第三亮」至少四群），兩者取大。

CPODE 那兩格怎麼回來的：它跟 MG **共用 pitch**（使用者給的關鍵），所以填了 MG 的
pitch 之後，那兩個位置就是晶格補回來的 `filled` —— 它們本來就是同一排的一部分。
`kinds=3` + `pitch=24` 的結果是 6 格（4 根 MG + 2 個 CPODE），框在兩種格上離線的
距離完全相同。反過來 `select=darkest` + `kinds=3` 就只拿那兩根 CPODE。

### 給定線寬（「MG 線寬理論上要一樣，或給一個可以直接輸入的地方」）

第四輪的結論是「量的不是假設的」，而且**那個結論仍然成立**（線寬本身可能就是要
量的東西）。但它漏了另一半：使用者從 GDS 就知道線寬，而他要的不是量它，是拿它
**當尺**。

新參數 `vertical_width` / `horizontal_width`（0 = 照量到的）。它真正買到的東西是
**把一個問題拆成兩個**：給了線寬之後，這條曲線只剩一件事要做對 —— 每一根線的
**中心**在哪。中心是整段的重心，比單邊的邊界穩得多（邊界靠梯度的峰，糊掉一點
就飄），而 sensitivity 調的正是邊界。**線寬一旦固定，敏感度就從「決定框放在哪」
降級成「決定有沒有找到這根線」—— 而後者面板上看得出來，前者看不出來。**

三個細節：

* **給的是寬度不是位置。** 中心仍然來自影像 —— 不然這個參數就變成「假裝這裡有
  一根線」，那是另一件危險得多的事。
* **邊上只露半根的線是切掉，不是推回影像裡。** 推回去等於捏造一個不存在的位置，
  而框正是貼著它放的。
* **跟 pitch 是分開的兩件事**（一個講「每隔多遠有一根」，一個講「一根多寬」），
  所以只知道其中一個也用得上。

面板摘要會講 `width 8.0 px (given)` —— 只有**給定**的才講。量到的線寬畫面上本來
就看得到（塗起來的那幾段有多寬），給定的那個是使用者填進去的假設，而假設要看得到
才驗得了。

合起來正好是使用者描述的流程：**profile 定出 MG 中心 → 給定 MG 寬度 → 從 MG 邊界
往外長 ROI**（`place=beside_vertical` + `gap`）。

驗收 `tests/test_roi_cross_lattice.py`（14 條，含一條刻意鎖住舊陷阱：三種材質分兩群
時 pitch 會剛好變一半 —— 哪天分群改法了那條會紅，那正是要停下來看一眼的時候）。

## 6f. 第六輪：批次能不能信（來自「這樣夠 robust 嗎」）

使用者問：「這樣的設定方法通用性會不會不夠 robust，我是要 batch 去跑 patch 的，
然後也要能跨站點比，這個真的是好方法嗎？」

先量，再答。300 顆混合批次（相位隨機、雜訊/增益/偏壓漂移、一半有 CPODE），
一份固定 recipe：

| | 定位正確 | 定位錯誤 |
|---|---|---|
| `kinds=0`（當時的預設） | 166 | **134（44.7%）** |
| `kinds=3` | **299** | 1 |

好消息是「per-patch 的事寫成 per-recipe 常數」這個疑慮站得住 —— 那批裡有一半
根本沒有 CPODE，`kinds=3` 照樣 0.50 px（分群切在最大的間隙上，多切的那一刀
落在雜訊裡）。壞消息是另外一件事：**那 134 顆錯的裡面有 68 顆的
`pitch_error` < 0.5，而且信心值比正確的那些還高**（285.9 vs 215.8）。

### 為什麼既有的數字抓不到

`pitch_error` 問的是「我挑的這幾根**等距**嗎」。鎖在空隙上的時候，空隙也是完美
等距的 —— 所以那個數字是 0.00，而框在錯的地方。真正該問的是「我挑**對**了嗎」。

### 那個問題有一個免費的答案

**把量到的間距跟填進去的比一比。** 兩個數字程式裡都已經算好了，只是從來沒有
互相比對過。四種檢查各自量過（同一批 300 顆）：

| 檢查 | 擋掉錯的 | 誤擋對的 |
|---|---|---|
| 極性（選中的真的比其餘亮嗎） | 74/134 | 0/166 |
| 根數 ≤ 晶格點數 ×1.35 | 60/134 | 0/166 |
| **量到的 vs 填進去的** | **134/134** | 0/166 |

**只擋小的那一邊**，而這個不對稱是有道理的：

* 量到的**比較小** = 挑進了不該挑的東西（空隙、別的材質）。補線救不了 ——
  晶格會鎖上一組自洽但錯的解，而且看起來完美。
* 量到的**比較大** = 有幾根沒抓到。那正是補線存在的理由，補完就對了。

實測兩群完全分開（正確 0.95–4.95、錯誤 0.50–0.50），門檻設在 0.80。順帶接得住
「換一台機台、pixel size 不同」那種情況（真實 18、填 24 → 0.75）。

比的是**最小的相鄰間距**，兩邊都取 min：量到的那個數字是「相鄰兩根有多遠」，
而交錯的排法裡那個值就是兩個 pitch 裡小的那一個。拿平均去比的話，一排真正的
24/36 交錯會量到 24、對上平均 30，比值 0.80 —— 一個完全正常的 layout 就被判成
「挑錯組」。

### 處置：**失敗**，不是警告

框的位置錯了，那顆的每一個數字都是別的東西量出來的。留著它比丟掉它危險 ——
它會混進整批的統計裡。所以走既有的定位失敗路徑（退回整張圖、`locate_ok = 0`、
帶一句講得出下一步的理由），批次篩得掉。

`cross_pitch_ratio_x` / `_y` 也匯出成特徵：0/1 答不出「錯得多嚴重」，
而 0.50（挑錯組）與 0.75（pitch 本身填錯）的下一步不一樣。

### 還沒解掉的：跨站點

recipe 裡存的是**機台相依**的數字（px），而站點手上的知識是**設計相依**的
（GDS 的 nm，跨站點同一個值）。正確的分工是 recipe 存 nm、每個 dataset 帶一個
`nm_per_px`（`core/calibration.py` 留著就是為了這個，見 §8）。這一輪只做到
「填錯的時候會被擋下來」，沒做到「同一份 recipe 直接搬過去」。

驗收 `tests/test_roi_cross_trust.py`（9 條）。

## 6g. 第七輪：一鍵校正 —— pitch 是設計常數，整批一起量

使用者原話：「我不會只有一張 patch（可能有 50 張 100 張），直接用這些 patch
calculate 就可以找出一個最好的設定？因為你現在的 Use 彼此算之間還是有
variation。」順帶回報「Use」按鈕被切邊（只看得到一半的數字）。

他說的兩件事都是真的。切邊是 `shape="square"` 的 QSS（`max-width: 22px`）鎖死
文字按鈕；variation 是單張量測本來就有的 ±0.5 px 雜訊 —— 而 **pitch 是設計
常數**，這一批每張量的都是同一個數字，聚合就把雜訊除掉。

### 聚合的層級：原始間距，不是每張的結論

第一版聚合每張的 `pitch_measured`，在交錯的 layout 上安靜地錯掉：128px 配
40/33 的 patch 大多只看得到三根線，單張的結論是 **36.5** —— 一個沒有任何一對
線真的距離 36.5 的平均值，而且 50 張彼此完全同意這個錯的數字（agree = 1.00）。
把 50 張的間距倒在一起是一百多個樣本，40 與 33 兩群一目了然 —— 批次的價值正是
把「每張三根線」變成「一批一百個間距」。

### 分群之後的判讀（每一支都對應一個真實案例，六個情境全數實測）

| 樣子 | 判讀 | 結果 |
|---|---|---|
| 一群（29.333 批） | 單一 pitch | 29.000（誤差 0.000） |
| 兩群、比值非整數、同張 patch 裡交替 | **交錯** | 40.0 / 33.0 |
| 兩群、比值整數、高群**零星** | 缺線（含被 kinds 跳過的 CPODE 格）→ 摺回 | 24.000 |
| 兩群、比值整數、兩群**一樣多** | 挑錯組 → **拒填**，講出兩群 + 指向 kinds | note |
| 沒有一張過信心閘門（純雜訊批） | 沒東西可量 | note |
| 混批（30 好 + 8 雜訊） | 統計吃掉例外 | 24.00，n=30/38 |

「缺線 vs 挑錯組」分不開的教訓：先試了**純度**（同一張 patch 有沒有混群）——
被資料打臉，挑錯組的批 mixing 有 0.36（污染的 patch 自己就會混）。真正分得開
的是**豐度**：缺線是零星例外（每缺一根才多一個整數倍樣本），挑錯組的兩群一樣
多（實測 118 vs 130）。

鐵則不變：**批次自己不同意的時候不要硬給一個數字** —— 中位數會落在其中一群上，
看起來像個答案，但它不是。拒填 + 紅字講出兩群（「24 of them measure about
12.0 px…raise 'how many kinds'」）。

### 接法

`CrossInspector` 頂上一顆 `Measure pitch & width from this lot`（量測尺是手動
單段、`Use` 是自動單張、這顆是自動整批 —— 同一件事的三個尺度）。收集影像走
`collect_source_images`（跟區域檢視同一條路：**跑 pipeline 到這張卡為止**，
量卡片實際看的那條流，上游有 Enhance 時量原始檔就量錯了對象）。背景執行緒
（`CalibrateWorker`），量完走 `set_param` 填回（可復原、參數表跟著更新），
量的途中換卡不會寫進錯的卡。一好一壞時兩邊都講 —— 只報壞消息的話，使用者會
把填好的那一半也改掉。

使用者要的「只填 box width 跟 kinds」大致成立：pitch（含交錯）與線寬都變成
量出來的；留給人的是**意圖**（挑哪種材質、框放哪、多厚）與**影像講不出的事實**
（kinds）。

驗收 `tests/test_roi_cross_calibrate.py`（9 條）+ `tests/test_ui_f8_calibrate.py`
（7 條，含一條量按鈕放不放得下自己的字）。

## 7. 沒做的

* **`roi_profile` 沒有被取代。** 只要一段條帶的場合它仍然更簡單。
* **框只有正矩形。** 旋轉的 layout 要先轉正（沒有卡片做這件事）。
* **兩組以上的條紋**（例如三種材質交錯）沒有處理。
* **`max_boxes` 砍掉的是最外圍的**，而且只在 `reason` 裡講一句。
  框很多的時候使用者不一定會看到。
* **pitch 仍然要人填，而且要自己換算成 px。** 站點知道 nm（GDS）也知道
  pixel size（機台設定），但卡片上沒有這兩格 —— 使用者得自己算 44 / 1.5。
  要做的話該接 `core/calibration.py`（§8 留著就是為了這個），
  而不是在卡片上再開一個會忘記填的 nm/px 欄位。
* ~~**線寬不能覆寫。**~~ 第五輪做掉了（`vertical_width` / `horizontal_width`）。
* **量測尺量不到 nm。** 它報的是像素，因為 `nm_per_px` 沒有來源（§8）。
  接上 `core/calibration.py` 之後這裡可以同時報兩個單位。
* ~~**ROI mask 影像流 + 只用 mask 內像素的正規化**~~ **第六輪做掉了
  （2026-08-14）**：`roi_mask` 卡（具名區域 → 0/255 影像流；多名字 = 聯集；
  `regions` 留空是 `not-configured`，畫布掛警示）+ Normalize 的 `Use only`
  （`use_within`，percentile / glv_band 才出現）—— 範圍只從 mask 內量、
  **套用仍是整張圖**。驗收照原話量（`tests/test_roi_mask.py` 最後一支）：
  「一根 MG 進出畫面」時，「只用 EPI」的 EPI 亮度分散度收斂到整張圖版本的
  一半以下。實驗設計時學到一課：整張圖的 percentile 最痛的不是 MG 12% ↔ 24%
  的變動（p98 兩邊都落在 MG 上，反而穩），是面積**跨過百分位門檻**的那一下
  （0% ↔ 12% 之間 p98 從 EPI 的頂翻成 MG 的 230，同一片 EPI 的輸出從 ~130
  掉到 ~20）—— 而那正是條紋在 crop 邊緣進進出出的樣子。界線守住：mask 給
  **影像段**用，量測卡照樣引用 ROI 名字。mask 尺寸對不上時 StepError 指名
  去改 `Size like`；全 0 的 mask 退回整張圖並 `ctx.warn`（不安靜）。
* **跨站點要重填一次 px。** 見 §6f 最後一段 —— 現在只會擋，不會換算。
* **CPODE 的格子分不出來。** 補回來的那兩格跟 MG 那幾格在輸出上長得一樣
  （同一個 ROI 名字、同一批框）。要分開打分的話得讓 `filled` 的那幾格帶自己的
  標記 —— 目前只有一個整數計數。
* **`kinds` 要人填。** 理論上可以從曲線的直方圖自己數台階，但「數錯了」與
  「使用者填錯了」的處置完全不同，而前者沒有地方可以講。
