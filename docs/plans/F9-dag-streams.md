# F9 —— 影像流的身分綁在「線」上（真正的 DAG）

> 狀態：**進行中** —— F9-0（黃金值）✅、F9-1（邊帶埠）✅、F9-2（卡片只看得到
> 自己宣告的輸入）✅、F9-3（特徵掛節點 + 撞名救援）✅、F9-4（快取帶得動歸屬）✅、
> F9-5a ✅、F9-5b ✅、F9-6 ✅（同進同出的埠 + 來源唯讀）、
> F9-7 ✅（線全部由使用者拉、一個輸入埠一條線）、
> F9-8 ✅（快取看得見線、停用的卡沿線讓路；§12）、
> F9-9 ✅（一對節點之間可以有好幾條線 —— 多連一／一連多）、
> **F9-10 ✅**（分支 + 快取：選擇性存 + 缺了就重算）、
> F9-5c 只剩「沿線可見」的一小塊（見 §7 的註）
> 三個決策（§6）使用者已於 2026-08-16 全部同意
> 前置：F8 已完成；存檔 recipe 已移除；範例 recipe 已清空

## 1. 一句話

把影像流的身分從**全域的名字**改成**「哪個節點的哪個輸出埠」**，
於是同一條 `ref` 可以分岔成兩條互不干擾的支線，而每條線帶著自己的 feature。

## 2. 為什麼是現在

B 一向最貴的部分是**相容性** —— 改資料模型會讓使用者手上的 recipe 全部失效。
而這一刻：

- **存檔 recipe 已經移除**（2026-08-16），使用者手上不會有任何 recipe 檔；
- **範例 recipe 已經清空**（`examples/` 整個移除）；
- repo 裡的 recipe 只剩 `tests/fixtures/recipes/` 兩份，是我們自己的。

**所以遷移成本現在是零，之後只會變貴。** 這是做 B 最便宜的時間點。

## 3. 現在是什麼樣子

| | 現況 |
|---|---|
| **執行順序** | ✅ 已經是 DAG —— `execution_order()` 對 `route 相鄰對 ∪ edges` 做拓撲排序 |
| **資料** | ❌ 全域名字表 —— `Context.images` 是 `{"test": arr, "ref": arr, "diff": arr}` |

分支做不到的原因**在資料不在順序**：兩條分支各自處理 `ref`，寫回的是同一個
格子，後寫的蓋掉先寫的 —— 結果不是分支，是串聯。

```
        ┌── denoise A (ksize=3) ──▶ 寫回 ref
ref ────┤
        └── denoise B (ksize=9) ──▶ 寫回 ref     ← 蓋掉 A
```

## 4. 核心設計：卡片一行都不用改

**這是讓 B 從「重寫引擎」變成「改引擎的接線」的關鍵。**

卡片現在的樣子是：

```python
def run(self, ctx, params):
    img = ctx.require_image(params["source"])    # 用名字要一張圖
    ctx.set_image(params["out"], result)         # 用名字寫回去
```

新模型**不動這個介面**。改的是「跑一張卡之前，`ctx` 裡有什麼」：

```
現在   ── 一個 ctx 從頭傳到尾，每張卡都看得到所有流 ──
        load ─▶ ctx{test,ref} ─▶ denoise ─▶ ctx{test,ref} ─▶ subtract ─▶ …

之後   ── 每張卡拿到的是「照它的線組出來的」一個小 ctx ──
        produced[(load,"test")] ─┐
                                 ├─▶ denoise 看到 ctx{test}      → produced[(denoise,"test")]
        produced[(load,"ref")]  ─┴─▶ …
```

引擎多做兩件事，卡片全部無感：

1. **跑之前**：照這個節點的**入線**組一個只含它該看到的流的 `Context`；
2. **跑之後**：把它寫出來的流收成 `produced[(node_id, out_name)]`。

> **F9-2 只做了第 1 件。** 第 2 件（產出改用 `(node_id, out_name)` 當身分）留到
> F9-5 —— 因為那一步才會真的改變可觀察的行為，而 F9-2 的目標是「機制建立起來、
> 數字一個都不動」。目前產出仍然收回全域表（名字 → 最後一個寫它的人），
> 所以快取、預覽、trace、黃金值全部原樣。

`Step.run()` 的簽章、17 張卡的程式碼、`ParamSpec`、`validate_params`
**一律不動**。I3 那條測試（宣告什麼就只碰什麼）正好是這件事的前提 ——
卡片如果會偷讀沒宣告的流，這個模型就組不出正確的小 `Context`。
**先有 I3，B 才安全**（已於 2026-08-16 完成）。

### 4.1 邊要帶什麼

```
現在：edges = [[src_node, dst_node], …]
之後：edges = [[src_node, src_out, dst_node, dst_in], …]
```

`src_out` = 來源節點的哪個輸出埠（`"ref"`）；
`dst_in` = 落在下游卡的哪個**輸入參數**（`"b"`、`"streams"`…）。

綁**參數名**而不是流名，是因為流名之後只是**顯示用的標籤** —— 使用者把
`ref_2` 改叫 `ref_soft`，接線不該因此斷掉。

### 4.2 feature 也跟著線走

```
現在：ctx.features = {"glv_max": 12.0, …}                 扁平、全域
之後：produced_features[(node_id, "glv_max")] = 12.0      綁在節點上
```

匯出（CSV／KLARF／score 表達式）時**攤平成一個名字**。攤平規則見 §6 決策 D2。

> **F9-3 的實作取捨（重要）**：既有語意**一個字都沒改** —— 撞名時 `glv_max`
> 仍然是「最後一張卡寫的值」，score 表達式、CSV、KLARF 照舊。改的只有一件事：
> 以前被蓋掉的那份**完全消失、指都指不到**，現在它留了下來，叫
> `<前一張卡的節點名>_<原名>`。
>
> 為什麼是「救回舊的」而不是「把新的改名」：後者會讓 `glv_max` 突然不存在，
> 一份跑得好好的 recipe 的 score 表達式當場失效。救回舊的是**純粹加東西**。
>
> 歸屬記在 `ctx.meta["feature_owner"]`（不是 `DefectResult` 的新欄位）——
> 加欄位就要動 SQLite schema 與 CSV，而驗收條件是「沒撞名時逐位元組相同」。

## 6. 要先定的三個決策

### D1. defect 層級與跨線的 feature 掛哪

有三類 feature 天生不屬於單一條線（都在使用者的截圖裡出現過）：

| 例子 | 它描述什麼 |
|---|---|
| `n_channels` | 這顆 defect 有幾張圖 |
| `align_dx` / `align_dy` / `align_score` | **兩條線之間**的關係 |
| `cross_count` / `locate_ok` / `cross_pitch_*` | **具名區域**的屬性（`roi_cross` 吐的是框不是影像流）|

**提案**：feature 一律掛在**產出它的節點**上（不是線上）。節點本來就只有一個，
所以三類全部有明確的家；「沿著線累積」變成「沿著**線的上游節點集合**累積」，
語意一樣而且沒有例外。

### D2. 攤平成什麼名字

匯出與 score 表達式需要扁平的名字。**提案**：

1. 沒有撞名 → 就用原名（`glv_max`）。使用者看到的跟現在一樣。
2. 撞名 → 自動加前綴，前綴預設是**那條線的名字**（`ref_soft_glv_max`）。
3. 使用者仍可用 `output_prefix` 自己指定。

好處：不用發明 `ref_soft.glv_max` 這種語法 —— 寫 score 的是不會寫 code 的
工程師，多一種語法就是多一道牆。

### D3. 快取的切點

現在的 checkpoint 是「執行順序上最後一張影像段卡的下一格」。DAG 之後那不再是
一個點。**提案**：快照 = checkpoint **之前所有節點的產出集合**，
key 照舊是 recipe 簽章；`FORMAT_VERSION` +1 讓舊快取自動失效。

> **F9-4 的實際內容比提案小，而且理由值得記下來。** 「產出集合」要到 F9-5
> （產出改用 `(node_id, out_name)` 當身分）才存在，所以 F9-4 不做那件事。
> 但 F9-3 留下了一個**真的會咬人的**問題：checkpoint 之前的節點在熱跑時根本
> 沒有執行，所以「誰產出了哪個特徵」那份帳只能從快照回來 —— 掉了的話熱跑不會
> 救被蓋掉的特徵，**冷跑多一個、熱跑少一個，而兩邊都跑得完**。
>
> 實測它目前是**通得過的**，但那是意外不是設計：`feature_owner` 剛好非私有且
> JSON-safe，所以被 `_meta_snapshot` 的通則收進去了。已用
> `test_feature_ownership_survives_a_cache_hit` 釘住（把它從快照拿掉 → 當場紅），
> 並在 `_meta_snapshot` 標明它是承重的。
>
> `FORMAT_VERSION` 2 → 3：欄位名稱沒變，但**舊快照沒有那份帳**，繼續用會餵回
> 跟冷跑不一致的結果。

## 9. F9-5c 的「輸出改名」為什麼不做了（2026-08-16）

計畫原本寫「分支時輸出要改名（`ref` → `ref_soft`），否則兩支分不出來」。
做完 F9-5a 之後發現**那個前提不成立**：

流的身分已經是 `(節點, 埠)`，而**邊本身就指明了資料從哪個節點來**。所以兩支
都叫 `ref` 完全沒有問題 —— `Edge(dn_soft → m_soft)` 與 `Edge(dn_hard → m_hard)`
分得清清楚楚（`tests/test_dag_branching.py` 就是這樣寫的，兩支都叫 `ref`）。

改名剩下的價值只是**畫面好讀**（`ref (from dn_soft)` 比兩顆都叫 `ref` 好認），
那是顯示的事，不是資料模型的事。列進 backlog，不擋任何功能。

這也回答了當初 B vs C 的爭論：**選了 B 之後，C 的自動改名機制就不需要了** ——
它本來就是「沒有真正身分時的替代品」。

## 10. 還沒收的尾：`_unmet_needs` 仍然是線性的

Studio 的「這張卡少了什麼上游」用 `available_streams(before_node=…)` 算，
而那個函式是照 **route 的線性順序**累加的，不是沿著線走。有明講的邊時它可能
報一個假的缺口（畫面上有線、它卻說少一條）。

沒有跟著這一輪修，是因為 F9-6 之後**參數表單不再用那份清單**（來源改成唯讀
顯示），所以它現在只影響一句提示文字，不影響任何計算結果。

## 11. F9-7：線全部由使用者拉（2026-08-16 使用者回報）

使用者的話：**「新增卡 不要自己接線（線都給 user 接）」**，附了一張畫布截圖 ——
`Load images` 同時接進 `Denoise` 與 `Adjust tone`，而 `Denoise` 的輸出也接進
`Adjust tone`：同一個輸入埠上有兩條線。

### 那樣接會怎樣（使用者問的第二題）

引擎查「這個節點的這條流從哪來」的 key 是 `(下游節點, 流名)`
（`engine._explicit_bindings`）。兩條線落在同一個 key 上時，**`dict` 後寫的贏**
＝ `recipe.edges` 裡排在後面的那條 —— 而那個順序在畫布上完全看不出來。
症狀是「我明明接了 Denoise，跑出來卻像沒接」：跑得完、有數字、而且是錯的。

### 病根是自動接線

那條 `Load → Adjust tone` 使用者從來沒有畫過 —— 是舊版 `add_card_after`
加卡時順手接的。立意是少按一次，代價是畫布上有**第二個作者**。

### 這一段做了三件事

1. `add_card_after` **不再產生任何線**，也不再幫新卡改來源參數。順序照排
   （「在這張之後做」跟「資料從這來」是兩件事）。
2. 往同一個輸入埠再拉一條線 → 舊的那條**讓位**（`_drop_conflicting_edges`），
   狀態列講出換掉了誰。`image_keys` 的卡上不同流名的線照樣並存
   （一條 test、一條 ref 是兩個 key，本來就該共存）。
3. `recipe.validate` 新增 `ambiguous-input`（error）—— UI 擋得住是因為它會換線，
   直接編 JSON 的人沒有那道關卡。

順帶：拉一條線現在是**一步復原**（`_on_edge_added` 包進 `compound`）。
以前那是三、四步，按一次 Ctrl+Z 會停在「線還在但埠沒了」。

### 沒做的事

沒有把新卡的來源參數清成空字串。清了畫面會更誠實（沒有線就顯示
「not wired yet」），但參數的預設值是**recipe 的語意**：省略 = 用卡片預設，
清成空字串等於讓 GUI 產出的 recipe 跟手寫的不一樣，而且每張新卡在接線之前
都會 lint 失敗。要做的話得連 lint 訊息一起設計，列進 backlog。

## 12. F9-8：分支之下的四個洞（2026-08-16 稽核）

F9 把身分改成 `(節點, 埠)` 之後，做了一次針對**分支路徑**的稽核（用可執行的
探針，不是讀程式碼推論）。找到四個「跑得完、有數字、而且是錯的」，全部同一個
病根：**身分改了，但快取、停用、以及邊的儲存這三處仍然用全域名字在想事情**。

線性 pipeline（＝目前所有既有 recipe）不受任何一個影響 —— 黃金值三組 22 顆
逐項相同。

### 已修（F9-8）

| | 症狀 | 修法 |
|---|---|---|
| **1** | 改一條線、重跑，**數字沒動** | 影像段裡的線進簽章（`image_segment_signature`）。改接線可以完全不動參數，所以簽章非看線不可 |
| **3** | 停用分支中間那張卡，下游吃到**另一支**的值 | `_follow_disabled`：沿那條線自己的入線往上找第一個還開著的產出者；找不到就讓卡片看不到這條流（報缺），不是給它別人的圖 |

迴歸測試：`tests/test_f9_8_cache_and_disabled.py`（6 條，其中 3 條在修之前是紅的）。

> 簽章改了 = **既有快取全部失效一次**。那是冷重算，不是錯誤。

### 還沒修的那一個

**2. 分支 + 影像段快取：冷跑 ≠ 熱跑。**
快照存的是 `ctx.images`（名字 → 最後一個寫它的人），`produced[(節點, 埠)]` 沒
進去。熱跑時指向快取段內某個節點的線查不到，退回最後寫者 = 另一支。
實測 `m3_mean` 冷跑 3.0、熱跑 5.0。

修法是把 `produced` 也存進快照（`FORMAT_VERSION` → 4）。**要定調的是存多少**：
全存會讓快取檔按中間影像的張數倍增；只存「被跨越 checkpoint 的線引用到的那
幾條」則幾乎不變大，但實作要多一次分析。

**4.** ✅ 已於 F9-9 修掉（見 §13）。


## 13. F9-9：一對節點之間可以有好幾條線（2026-08-16 使用者定調）

> 「當然要可以兩條並排（我說過要很 flexible）。**餵圖是節點跟節點間在處理的**，
> 卡片只負責『餵進來的這些 source 要怎麼處理並再把 result 丟出去』。
> 所以理想上可以多連一，也可以一連多。」

這句話把責任切乾淨了：**接線是節點之間的事，處理是卡片自己的事**。卡片不必知道
資料從哪來，節點之間也不必知道卡片要怎麼處理 —— 而「一對節點只能有一條線」正好
違反了前半句。

### 改了什麼

- `Edge` 的「重複」判準從**兩個節點**改成**整條線**（兩個節點 + 兩個埠）。
  `RecipeModel.has_line()` 是新的判準，`has_edge()` 保留給「這兩張卡之間有沒有
  依賴」（成環檢查、排版）。
- `set_edge_ports` 優先挑**埠是空的**那一條 —— 補埠不可以去改已經有埠的鄰居。
- `remove_edge(src, dst, src_out=None)`：給了 `src_out` 就只拿那一條。
  線上的剪刀（×）現在帶著自己那條的流名（`edge_removed` 多一個參數）。
- 畫布從 `model.edge_lines()` 拿「每一條線 + 它從哪顆埠出發」**照著畫**，
  不再從「兩端共用哪幾條流」推。推出來的猜不出使用者其實只接了其中一條。
- `_connect` 先算出 `dst_in`（純查表）再把線**連埠一起**加進去。以前是
  「先加一條沒埠的線，再回頭補埠」，而補埠只找得到第一條。
- 剪掉一條線會把那條流從下游卡的參數裡拿掉（`_unpoint_stream`）——
  否則畫布會**反過來**說謊：線沒了，卡片還在處理它。
  **最後一條不清空**：`MultiStreamStep.stream_list` 對空字串是
  `keys or ["test"]`，清成空的那張卡會安靜地跑回 test。

### 沒變的規則

F9-7 還在：**同一個輸入（同一個參數上的同一條流名）只能有一個來源**。
「多連一」指的是不同的流各走各的線，不是同一條流有兩個來源。

迴歸測試：`tests/test_ui_f9_9_two_lines_side_by_side.py`（9 條，修之前 6 條是紅的）。


## 14. F9-10：分支 + 快取（§12-2，已修）

**症狀**：同一份**分支** recipe 跑第二次，某些數字變了（`m3_mean` 冷跑 3.0、
熱跑 5.0）。線性 recipe 不受影響。

**因**：快照存的是 `ctx.images`（名字 → 最後一個寫它的人），
`produced[(節點, 埠)]` 沒進去。熱跑時指向快取段內某個節點的線查不到，
退回最後寫者 = 隔壁那一支。

**要注意的取捨**（2026-08-16 討論）：直覺的做法是「只存有人在用的那幾張」，
但那有一個洞 —— **「誰在用」取決於 checkpoint 之後的線，而那些線故意不在簽章裡**
（不然改一下算法段就要整段重算影像）。於是會出現「快取是有效的、但這次需要的
那一張沒存」的組合，而那正好又退回舊行為 = 安靜地拿錯圖。

所以選擇性存的話，**一定要配一條**：熱跑時要的 `(節點, 埠)` 不在快照裡 →
當成 **cache miss 重算**，不可以退回 `ctx.images`。有了那條防線，選擇性存就是
安全的，而且快取幾乎不會變大。

### 做法（2026-08-16 使用者定調「選擇性存 + 缺了就重算」）

- `_streams_needed_across_checkpoint()`：checkpoint **之後**的卡片，明講要吃
  checkpoint **之前**哪幾個 `(節點, 埠)`。那就是要多存的清單。
- **只算明講的線。** 推出來的（`_implicit_bindings`）本來就是「最後一個寫這個
  名字的人」，那正好等於快照裡的 `images` —— 退回去拿到的是同一張圖。
  所以**既有的（沒有埠的）recipe 一張都不必多存，快取大小完全沒變**；
  只有真的在畫布上拉了線的地方才付這個代價。
- `StageCache` `FORMAT_VERSION` → **4**（多了 `produced`）。舊快照版本不合一律
  當 miss，不會餵回缺欄位的東西。
- 防線：`run_defect_cached` 拿到快照之後先比對「這次要的」是不是「快照有的」的
  子集，不是就**當 miss 重算**。

代價是一種 ping-pong：在兩條算法段的線之間來回改（A→B→A），每次都會重算一次
影像段。那是正確的行為，而且那個編輯樣式很罕見 —— 存兩邊的聯集會讓快取無上限
地長大。

迴歸測試：`tests/test_f9_8_cache_and_disabled.py` 的 §1b 三條（修之前全紅）。
