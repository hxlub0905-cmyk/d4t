# F51 — 特徵名只有一個真相（2026-08-28）

**狀態：✅ A ＋ B ＋ C 完成**（C 於 2026-08-28 做完，見 F57；
⚠ 下面 §6 對 C 的描述**有一句是錯的**，那一節有訂正）。

起點是使用者的一句話：「Feature 部分你覺得有什麼地方可以修正改善」。查下去
找到一個**真的 bug**，而其中一半是 F50 那一輪自己種的。

---

## 1. 「誰產出這個特徵」有三份實作

| 住哪 | 什麼時候算 | 誰在用 |
|---|---|---|
| `engine._rescue_overwritten_features` | **執行期（真相）** | CSV / KLARF / 分數表達式 |
| `verdict_features.bound_specs` | 靜態預測 | 結果表分層、雙層表頭、維度過濾、回溯面板 |
| `viewmodel.feature_owners` | 靜態預測（更弱）| 幽靈線／淡線 |

而**兩份預測跟真相都對不上**。實測（一份 recipe 放兩張 GLV 卡，跑一次）：

```
引擎真的寫出來的: glv_glv_max  glv_glv_mean  glv_glv_pixels  glv_glv_q99
                 glv_max      glv_mean      glv_pixels      glv_q99
UI  說會有的    : glv2_glv_pixels  glv_glv_pixels
                 glv_max  glv_mean  glv_pixels  glv_q99
```

三個後果，一個比一個嚴重：

1. **幽靈欄** `glv2_glv_pixels` —— 結果表上一欄永遠是空的；
2. **看不到** `glv_glv_max` / `glv_glv_mean` / `glv_glv_q99` —— 引擎真的寫進
   CSV 的三個數字，畫面上分不了組、篩不到、回溯面板指不到；
3. **裸名掛錯卡** —— `glv_max` 被算在**第一張**卡上，而那個值來自最後一張。
   結果表的分組、回溯面板的「跳到產出卡」因此都跳到錯的卡。

### 為什麼會這樣：方向反了

引擎（`_rescue_overwritten_features`）的規則是**後寫的贏**：

* 最後一張卡的值留在裸名（`glv_max`）；
* **被蓋掉的每一張**被救成 `<它的前綴>_<原名>`。

而 `bound_specs` 寫的是相反的：第一張拿裸名、後面的拿救援名 —— 而且**只對
診斷數字**加救援名、還是**無條件**加（沒撞名也加，所以基準線上就有幽靈欄）。

## 2. A：三份收成一份

* **`bound_specs` 的救援規則改成跟引擎逐字一致**（裸名歸最後一張、前面每一
  張各拿一個 `<前綴>_<原名>`、沒撞名就不加）；
* **`feature_owners` 改成 `bound_specs` 的投影**，自己那個迴圈刪掉。
  它以前知道 23 個名字，`bound_specs` 知道 34 個 —— 差的 11 個是救援名與
  引擎特徵（`score`、`decide_unanswered`）。

### 那把尺（這一輪真正的產出）

`tests/test_feature_names_match_the_engine.py`：**真的跑一次引擎**，拿它的
keys 當基準，斷言兩邊逐項相同。三個案例（無撞名／複製 GLV／複製 CD）。

⚠ **尺一開始定太嚴，而放寬的方式很重要。** 第一版要求「UI ⊆ 引擎 ∪ 宣告」，
因為 `cd_*_nm` 這種「宣告了、但這批算不出來」的名字合法地只在 UI 那邊
（F19：算不出來的那一格不寫）。但那個放寬**也會放過真的發明出來的名字**。
所以改成**把落差的來源拿掉** —— fixture 把 nm/px 填起來，讓每一個宣告都真的
算得出來，尺就回到「逐項相同」。

> **放寬一把尺之前，先問能不能改掉讓它量不準的那個條件。**

## 3. B：淡線改吃那一份

F50 的淡線接的是最弱的那一份，於是**整個工具最常見的一條連結畫不出來**：

```
output_report.rank_by = "score"   →   淡線 0 條
```

兩個原因疊在一起，各修一個：

* **`feature_owners` 不知道 `score`** → A 修掉了；
* **`optional_features_in` 刻意排除 `score`** —— 對那支是**對的**
  （`score` 不是任何一張卡算出來的，lint 一開始就把它種進可用名單，永遠不會
  缺），但畫線問的是別的事。

所以多一支 `Step.feature_names_in`：**這張卡的設定上寫著哪些名字**。

| | 問什麼 | 誰用 |
|---|---|---|
| `resolve_features_in` | 少了會**失敗** | lint（error）|
| `optional_features_in` | 少了會**退化** | lint（warning）|
| **`feature_names_in`** | 設定上**寫著**哪些名字 | 畫線 |

實作是**機械的**：掃每一個 `feature_key` / `feature_keys` 參數。所以新卡片
不必覆寫它 —— 只要那一格宣告對型別（本來就該宣告，不然設定區長不出挑選器），
線就有了。`expr` 不掃：算式裡的識別字要 parse 才分得出來，那是判定段自己的事。

## 4. 翻面的那一條測試

所以翻面的方向就是修正本身。

## 5. 驗收

* **黃金值三份逐項相同**（這一輪只動預測，沒動引擎 —— 那正是要證明的事）；
* 核心 2773 綠、UI 逐檔全綠；
* 新測試 5 條 ＋ 淡線那一支補 2 條；
* **兩個舊行為各突變驗過會紅**（裸名歸第一個、沒撞名也加救援名）。

## 6. 沒做的：C

`feature-collision` 現在是 warning，而且**兩張同類卡都吐的診斷數字不報**
（理由是「每一份 recipe 都出現的警告會被學會忽略」）。於是使用者的
`glv_max` 被另一張卡蓋掉時，畫面上其實沒有人講。

要不要讓它變吵是產品決定，等使用者定調。**現在至少那個值找得到了** ——
救援名在結果表上有身分、在淡線上指得回它的卡。
