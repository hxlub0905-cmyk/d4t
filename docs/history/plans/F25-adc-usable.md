# F25 — 判定段要**有人會用**

> 狀態：第一輪已完成（2026-08-24）。
> 起因是使用者看過 F24 的成品之後的四句話：
>
> 1. 「ADC card 要更智能一點，讓人覺得很好用（**我目前不太知道怎麼用，
>    如果我都不會用其他人更不會**）」
> 2. 「UI 顯示（畫布下方）也有問題（**文字被裁掉**）」
> 3. 「**輸入 bin 有機會閃退**」
> 4. 「**加 ADC card 是要直接顯示在畫布上**，而不是要勾選 Sort into several
>    classes 才顯示（我甚至認為直接進去就要是 advanced 了，**原來的根本不會
>    用到**）」

---

## 1. 病根：我們做完了引擎，但入口是一格空白

F24 把判定樹做對了 —— 樹上畫布、分支流量、路徑亮起。但**使用者要先寫出
`contrast > 120` 這種東西**，這一段才會動起來。對不會寫 code 的製程工程師，
一個空白的算式框跟一面牆沒有差別：打錯一個字得到的是一條 `bad-rule`，
而畫面上看起來只是「這個工具不理我」。

四句話其實是同一件事的四個面：**入口太遠**（要先勾選）、**起點是空白**
（要自己想出一個算式）、**畫面說不清楚**（字被裁掉）、**碰它會壞**（閃退）。

## 2. 做了什麼

### 2.1 加 ADC 卡 ＝ 畫布上直接有一棵樹（不用勾任何東西）

* 卡片庫的 ADC 入口按下去 → `StudioWindow.add_decision()`：
  沒有判定就 `use_decide(True)`（**現有的門檻變成樹的第一個問題**，
  調了半天的那個數字不會消失）→ `ensure_tree()` → 樹只有一片葉子就
  `split_tree_leaf("")` 給一個起手問題 → 右欄跳到那一步 → **`fit()`**。
* 最後那個 `fit()` 不是裝飾：判定區長在所有卡片的右邊，而畫布多半停在
  左半邊 —— 不 fit 的話使用者按了 ADC 卡，**畫面上什麼都沒發生**。
* 「Sort into several classes」那顆勾選框**拿掉了**。分成好幾類現在是預設 ——
  而第二輪（§3.1）連二元門檻的編輯器都拿掉了，舊 recipe 一打開就是樹。
  機制（`use_decide`）一個字沒動。

### 2.2 問題不用打的：`[哪個數字 ▾] [比什麼 ▾] [多少] ＋ 滑桿`

一個問題大部分時候就是一句比較，所以那三格永遠打不錯：

* 數字從**這條 route 真的量得出來的**那些挑（`labelled_features`）。
* 比較是六個選項（is greater than / is at least / …），不是符號。
* 值配一支滑桿，**範圍取自流到這一步的那些顆的分布** —— 而不是
  ±1e9 那種沒有意義的區間。
* 底下一行即時的數字：**「34 of the 48 defects that reach here say yes」**，
  拖滑桿的時候**就地更新**（不重建 —— 重建會把滑桿從手上搶走）。
  沒跑過就一個字都不畫（F18 的老規矩）。
* 複合條件（`(a > 5) * (b < 2)`）拆不成三格 → 誠實地回算式框，不猜。
  「Expression…」在動作列上隨時切得過去，切回來也行。

判準是 `parse_simple_condition` ／ `format_condition` 這一對純函式
（`ui/tree_scene.py`），round-trip 有測試釘住。**認不得就說認不得** ——
猜錯的那一次會安靜地改掉使用者的判定，而它跑得完、有數字。

### 2.3 新的一步不是空白：先擺一個問得出東西的問題

`suggest_condition`（純函式）：**挑這一批上分得最開的那個數字**
（四分位距 ÷ 中位數，量綱無關），門檻放**中位數**；使用者自己組的
working numbers 優先。它不是自動最佳化，是一個「按了就有東西看」的起點 ——
剩下的用滑桿調。沒跑過（沒有分布）就什麼都不填：那時候硬猜一個數字
比留白更糟。

### 2.4 閃退：拆版面不准銷毀正在發訊號的那一個

`widgets.clear_layout_parked()`。這幾個面板是「改一格就整段重建」的：
使用者動了某一格 → 訊號寫進 model → listener 打回來 → 面板重建 →
**舊的那一格就是正在發訊號的那一個**。`setParent(None)` 之後 Python 是
它唯一的持有者，layout item 一丟就當場解構 —— 而 Qt 的訊號還在那個物件的
堆疊上。那是 use-after-free：跑得完的時候什麼事都沒有，跑不完的時候是閃退，
**而且跟平台的事件流有關**（offscreen 重現不出來，真機上「有機會」發生）。

改成：拆下來的 widget 藏起來、從版面拿掉、**參考留著**，真正的解構排到下一輪
event loop。三個面板（判定、判定樹的一步、分流）共用同一支。

### 2.5 裁字

* 規則列拆成兩行（條件一行、`→ bin N ｜ 名字` 一行）。實測預設欄寬 437 px
  而八個元件要 590 px，於是名字那一格被壓成 92 px ——
  **`not measurable` 在畫面上變成 `measurable`**（一個意思相反的字）。
* 導引式那一列：比較與數值固定寬，名字吃剩下的。
* 按鈕不再撐滿整列（撐滿的按鈕讀起來像標題）。

## 2.6 分流（pre-filter）在畫布上：徽章，不是卡片（F25-B）

使用者 2026-08-24 的兩個問題與定調：

> 「ADC 要怎麼分 prefilter（**需要獨立一張 card 嗎**？）」
> 「如果是 prefilter 他的層級感覺跟 card 不一樣（蛋生雞），那**放在 ADC card
> 裡是否合理**？」

**兩個都是「不要」，而理由是同一條 —— 時間順序。**

* **不是一張卡**：卡片是在 route **裡面**跑的，而 pre-filter 決定的正是走哪
  一條 route（使用者自己講的雞生蛋）。它也不能是判定樹的一步 —— 那些變數是
  特徵，特徵要跑完才有。
* **也不放進 ADC 裡**：同一個論證再走一步。pre-filter 在**任何卡跑之前**、
  ADC 在**全部跑完之後** —— 它們是同一條 pipeline 的兩端。把最先發生的事
  畫進最後發生的那個框裡，就是畫布把順序講反了，而「畫布不能說謊」是這一
  路的最高指導原則（F10／F24 那批坑全是這個形狀）。

  ⚠ **編輯器裡它們本來就在一起**：`RouteByBox` 就在判定欄的最上面，由上往下
  讀正好是時間順序。使用者的直覺（「這兩個是同一類東西」）在那一層已經兌現
  了 —— 要分開的只有畫布，因為畫布的職責是順序。

* **做法**：一個站在所有卡片**前面**的徽章（`ui/route_badge.py`）——
  不可拖、不可選、沒有埠、接不了線（它不是 pipeline 的一步），一條虛線細
  箭頭指進第一張卡。上面三件事：看哪一欄、對照表長怎樣、**現在這一顆走哪
  一條**（粗體那一列，跟著換 defect 動）。試跑之後每條路右邊有顆數 ——
  **從 `route_taken` 讀**（F19 當初就是為了這件事把它寫出去的）。
* **兩者用同一套視覺語言**（虛線框、大寫標題、不是卡片、點了都去同一欄編輯），
  而且 tooltip 互相指認（「這是兩段分揀的第一段，第二段是右邊的 Decision」）
  —— 家族看得出來，順序沒有被弄反。
* 真正把分岔畫出來（一張畫布看到兩條支線）是 **C**：要 F17-⑤「一份 recipe
  一張圖」，大手術。使用者定調先做 B，等 route 真的開始漂再談 C。

### 3.1 二元門檻的 UI 拿掉了

* `DecidePanel` 的門檻編輯器整支刪掉。沒有判定的時候那一頁不再是「另一種
  判定」，而是**「還沒有判定」**加一顆「Add the decision」。
* **舊 recipe 一打開就自動變成樹**（`StudioWindow._adopt_threshold_as_a_tree`）：
  門檻變成第一個問題（`use_decide` ＋ `ensure_tree`），而且**不算改過**
  （`dirty=False`、清掉復原堆疊 —— 復原不該把使用者退回一個看不到編輯器的
  狀態）。
* **只在讀檔案那條路上做**，而且只在真的有 score 表達式時做 ——
  空白的新 recipe 不會被塞一棵樹（那是 ADC 卡的工作）。
* **這是 UI 層的遷移，不是引擎的**：`Recipe.load` 一個位元都沒動，CLI 照舊
  跑那份檔案的 `score`（黃金值因此不受影響），而 Studio 又存不了檔
  （2026-08-16 拿掉），所以磁碟上的東西不會被改寫。
* **行為保持有證據**：值網格逐點比，同一個分數表達式走老路與走轉出來的樹，
  score 與 bin 逐點相同（`test_converting_a_threshold_recipe_keeps_every_verdict`）；
  實跑 48 顆也是 48/48 相同。
* 一個誠實的落差：轉出來的規則是 `expr >= threshold`，而老路是
  `score < threshold` 判 below —— 兩者在**分數是 NaN** 時會分到不同的 bin。
  留 `>=` 是因為它讀起來才是正著的（「大於就是這一類」），而 NaN 的分數本來
  就是一份算壞了的 recipe。
* 連帶：畫布的 `score_summary` 以前自己組「score = … threshold …」，那句話
  之後永遠是空的門檻 —— 改成由 Studio 組（「decision tree · 3 questions」）。
  它從來沒有被畫出來過（判定區出現之後就是遺跡），但 API 不該說假話。
* ⚠ **直方圖上那條可拖的門檻線因此只剩歷史意義**：有判定的 recipe 它本來就
  藏起來（`_on_decide_mode`），而現在每一份開起來的 recipe 都有判定。
  同一個「一邊拖一邊看」的能力搬到了導引式問題的滑桿上（§2.2）。
